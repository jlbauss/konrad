## The big picture

konrad runs [opencode](https://github.com/sst/opencode) inside a sandboxed, rootless Podman container.

- **The image is the canonical artifact.** `image/Dockerfile` builds it; `bin/konrad` — a thin host-side bash CLI — is the primary consumer.
- **No IDE attaches to the sandbox — deliberately.** A `konrad init-devcontainer` (drive the sealed container from VS Code) was once planned and dropped: VS Code Dev Containers bridges every attached container to the host through sockets in `/tmp` — the host's `git credential` helper, the SSH agent, askpass, and the IPC channel, over which code in the container can install an extension that types commands into a *host* terminal. Microsoft treats this as by design, and no setting closes all of it (`gitCredentialHelperConfigLocation: none` still leaves the helper answering over IPC; SSH-agent forwarding has no off switch). Attaching would carry a host channel *inside* the firewall boundary and void "can't touch anything outside the workspace."
- **Podman, not Docker.** Open-source, free for commercial use, ergonomic on macOS. `--userns=keep-id` shares the container `node` user's UID with the host user, so bind-mounted files have sane ownership. Docker support is on the roadmap.
- **Two engines, one abstraction.** Podman is the default everywhere. On Apple-Silicon macOS 26+ with Apple's [`container`](https://github.com/apple/container) CLI present, konrad uses that native engine instead — dropping the `podman machine` VM. The two CLIs aren't subcommand-compatible, so every host-side engine call in `bin/konrad` goes through an `eng_*` wrapper and `detect_engine()` fixes the choice once at startup (`KONRAD_ENGINE` overrides). apple/container needs no `--userns` (VirtioFS maps guest UIDs → the host user) and rejects the `:z`/`:U`/`:ro` mount suffixes, so those are dropped there. Its named volumes are also root-owned and can't be chowned (no `:U`), so the three persistent stores (secrets/cache/state) are backed by host directories under `~/.local/state/konrad/store/` instead — VirtioFS remaps those to the container user, the same way it makes the `/workspace` bind writable. The remap is per lookup: VirtioFS reports a file as owned by whichever guest uid asked, and the guest caches that answer briefly, so an ownership check can see root or a nested container's uid on a file node owns. Block-backed engine volumes would give real ownership but attach to one VM at a time, and `konrad code`'s config, tools and clone are shared across parallel sessions and repos, so they stay on VirtioFS and the ownership-checking tools are told to stand down instead: `konrad code` trusts the clone as a git `safe.directory` and sets `XDG_CONFIG_HOME` to its default, which podman then doesn't second-guess.
- **Tuned for Qwen3.6-class local models.** The agent prompt ([image/opencode/agents/konrad.md](image/opencode/agents/konrad.md)) is sized for a ~30B-class local model; the tested recommendation is `qwen/qwen3.6-27b`. Frontier models work fine; sub-10B ones may need prompt softening.

## Engineering ethos — lightweight, composed, low-maintenance

The guiding principle behind every other choice here: **konrad stays lightweight and leans on well-maintained building blocks rather than custom code.** Prefer configuring an existing tool over shipping bespoke machinery; drive ongoing maintenance toward zero, so konrad keeps working and current even through stretches when no one is actively developing it. (This is why model-discovery's custom plugin was dropped, the config deep-merge is a tiny self-contained step, and the whole pinning/rebuild story is a bot plus upstream registries.)

Its second face: **simple, logical, and smooth beats clever.** konrad should stay tidy and resist sprawl. A solution that *feels* surprising (e.g. the runtime user lacking write access everywhere in its own home) is a smell to fix at the structural cause, not a quirk to live with — today's quiet workaround is tomorrow's unexpected consequence. Accumulating complexity is debt to pay down deliberately; periodic cleanliness passes are part of the maintenance story.

## Configuration & instructions

Config is **layered, not replaced** — host-mergeable layers, folded left, last writer wins:

```text
baked image defaults   <   org layers (0..n)             <   user
/etc/konrad/…               ~/.config/konrad/org/<name>/      ~/.config/konrad/user/
```

- Each layer holds the same opencode pieces — `opencode.jsonc`, `agents/`, `skills/`, `instructions/`, `AGENTS.md`, `fonts/`. [image/entrypoint.sh](image/entrypoint.sh) composes the `opencode.jsonc` of each via [image/merge-config.js](image/merge-config.js) (an N-input deep-merge) before opencode loads anything. **Objects merge recursively; arrays replace** — which is why agent rules are added via `AGENTS.md` or `instructions/`, not by overriding the `instructions` array. (A layer may also carry an `allowed_hosts` file — konrad-specific, consumed by the egress firewall, *not* part of this opencode merge.)
- **`org/` is a container of named layers, and a subscribed layer is a managed git mirror.** `konrad org add <git-url>` clones a repo to `org/<name>/`; `konrad org sync` (riding every `konrad update`) does `git fetch` + `reset --hard @{u}` — local edits to tracked files are clobbered by design (the user's channel is `user/`, which always merges on top), a failed sync warns and keeps the last-good checkout (availability beats freshness for a defaults mechanism), and there is **no state file** — the in-place `.git` records URL and branch, so `org list` reads what sync will actually use. Layers fold in alphabetical name order (`10-`/`20-` prefixes steer precedence); a plain non-git dir is a valid manual layer that never syncs; a detached-HEAD checkout (a tag) is the pin mechanism. This is why an org ships updates by `git push`, with zero bespoke updater and **zero konrad auth code** — private repos work through the member's existing git credentials (forge CLI login or SSH), auth by composition. The entrypoint, [compose-allowed-hosts.sh](image/konrad-defaults/compose-allowed-hosts.sh), and the overlay loops all walk the *same* sorted enumeration, so precedence can't drift between channels — and the firewall derivation sees **every** layer's providers (a missed layer would silently block that org's internal endpoint).
- **The `hooks/post-sync` hook is a deliberate exception to "agent code runs only in the sandbox."** A layer may ship an executable `hooks/post-sync`; konrad runs it host-side after `add` and after every successful sync (cwd = the layer dir). It exists for the ~10% of org needs plain config can't express (mirror a corpus into `context/`, derive per-member identity from the org's own forge auth) and it *rides the branch*, so it self-updates with the layer — a freestanding script konrad merely pointed at would re-create the frozen-clone problem this design replaces. Trust model: **subscribing is trusting** — no prompt, no flag; the decision to add a layer is the decision to run its code, documented as the boundary. Context-mirroring stays hook territory only; konrad gains no declarative corpus-sync engine.
  - **The hook environment is a small, deliberate contract** (it was "no special env" until 0.23, when the dominant sync path became the unwatched background worker and `echo` stopped reaching a human). konrad exports `KONRAD_NOTICE_DIR` (where to drop notices — the layer's own channel to its members, see [below](#distribution--updates)), `KONRAD_LAYER_NAME` (so a hook needn't guess its installed name), and `KONRAD_HOOK_INTERACTIVE` (`1` on `add`/`sync`/`update`, `0` under the worker — so a hook picks `echo` vs. a notice without sniffing the tty). Everything else it still derives from the well-known `~/.config/konrad/` home, same principle as layer discovery. The hook is time-bounded (`KONRAD_HOOK_TIMEOUT`, default 120 s; a portable shell watchdog, since GNU `timeout` is absent on macOS) so an unwatched hang can't live until reboot.
- **Discovery is a well-known `$HOME` folder** (`~/.config/konrad/{org,user}`), not an env var or system path — because the macOS Podman machine only auto-shares `$HOME` into its VM, so a `/etc`-style path would be invisible there.
- **`AGENTS.md` is the user's slot; `instructions` is konrad's.** opencode loads both, additively. The system `instructions` channel: the baked `opencode.jsonc` declares one glob for the baked `instructions/` dir and one for the user's, and opencode expands them itself — skipping absent dirs/files, de-duplicating, preserving order (per opencode's `Instruction.systemPaths`). **Org layers can't get a glob of their own**: opencode expands an entry by globbing only its *basename* component (the dirname is a literal), so `org/*/instructions/*.md` could never match — instead the entrypoint **copies** each layer's `instructions/*.md` (and back-compat layer-root `AGENTS.md`) into the baked `instructions/` dir as `org-<name>-<file>`, where the baked glob finds them. That's the same mechanism as the generated egress allow-list file, and uniform with the per-layer `cp -r` of agents/skills — no `jq`, no config surgery, and the array-replace footgun never bites because only the baked layer declares the `instructions` array. The user's global `AGENTS.md` stays theirs alone (opencode auto-discovers it). Precedence, all additive: `environment.md → org instructions → user instructions → user AGENTS.md → project AGENTS.md`.
- The org layer is **defaults, not enforcement**: files in the user's own home, so "add-only" describes merge precedence, not a permission lock (and sync clobbers local edits, it doesn't protect them).
- **Model discovery is an inline entrypoint probe, and there's no baked `model`.** Provider endpoints ship pre-wired with empty model lists; at session start [image/entrypoint.sh](image/entrypoint.sh) runs [discover-models.sh](image/konrad-defaults/discover-models.sh) — for every provider with an explicit `options.baseURL` it probes `<baseURL>/models` in parallel (bounded, `KONRAD_DISCOVERY_TIMEOUT`s; `KONRAD_NO_DISCOVERY=1` opts out), drops embedding models, and merges the results *below* the composed config so discovery fills the picker but an explicitly-declared model still wins. Each model also gets its `limit.context` when the endpoint exposes a window (vLLM's `max_model_len`, llama.cpp's `meta.n_ctx`) — opencode's auto-compaction keys off that limit, so without it compaction never fires and the model is treated as unbounded; the probe never *guesses* a window (a wrong one mis-compacts), so servers that omit it from the standard `/v1/models` (LM Studio, Ollama) leave the model bare and the user declares `limit.context` if they want auto-compaction there. (opencode's schema requires both `limit` keys once the object is present, and no endpoint advertises an output cap, so a discovered `context` ships with a derived `limit.output` of `context/6` (floor 2048, capped at the window) which a declaration overrides — proportional because opencode both *subtracts* `limit.output` from the context to size its auto-compaction budget and sends it verbatim as `max_tokens`, so a flat or inflated value would shrink the usable window or exceed a real output cap.) It runs as the `node` user inside the sandbox and reads each provider key from the mounted `auth.json`, sending it only to the endpoint opencode itself would call — **through the firewall proxy** (curl honours `HTTP(S)_PROXY`) — so the key invariant holds (the host and the proxy-as-decider never see it) and authenticated *remote* endpoints are discovered too, not just keyless local ones. This is the inline replacement for the dropped `opencode-models-discovery` plugin (re-adding it cost ~16 s/run via config, or re-introduced a build-time install + a fragile upstream dep + a 3 s-per-provider *sequential* probe that stacked to ~9 s on macOS's connect-dropping podman-machine VM). A model *declaration* is still the way to pin custom options; opencode prompts for the model on first run and remembers the choice in the `konrad-state` volume. If opencode gains native `/models` discovery ([opencode#27554](https://github.com/anomalyco/opencode/pull/27554)), the probe can be deleted.
- **Tool permissions are sandbox-shaped and live once, globally.** The baseline `permission` block sits in [opencode-defaults.jsonc](image/konrad-defaults/opencode-defaults.jsonc) (top-level → every agent inherits it via the same deep-merge); per-agent blocks carry **only deltas**, since they merge over it. The model follows the boundary, not the action's scariness: the container is disposable and non-root, so the agent acts freely *inside* it (`allow`), `ask` is reserved for the one irreversible action that hits the user's real files (`rm -rf` in the `/workspace` bind), and `deny` covers the escape vectors — root (`sudo`), host container/cluster control (`podman`/`docker`/`kubectl`), and the secrets volume under `external_directory`. Network tools stay `allow` because the [egress firewall](#egress-firewall) — not a per-command gate — is the real network boundary. Both `allow` and `deny` are prompt-free; only `ask` interrupts, so prompts are rare by design. Subagents add `question: deny` (no user in their loop) and tighten `rm -rf` to a hard `deny`; [manual-transformer](image/opencode/agents/manual-transformer.md) is the worked example.

## State, secrets & isolation

**`.agent/` belongs to the agent end-to-end; framework state lives elsewhere.**

```text
.agent/
  task.md                     # planning artifact (committable)
  artifacts/                  # durable mid-task outputs (committable)
  scratch/                    # agent scripts / probes
  quality-assurance/<stamp>/  # verification evidence on a fail
```

- **konrad doesn't touch the workspace at startup.** It neither creates the `.agent/` tree (the agent and the quality-assurance helper `mkdir -p` their own dirs on demand), nor prunes it, nor edits `.gitignore`, nor writes a session sidecar. The workspace bind is the agent's to shape — a launch leaves a clean repo clean.
- **A no-project launch gets an ephemeral scratch workspace, not a refusal.** `$HOME` can't be the workspace — it hands the agent the whole home, and the bind is refused outright on SELinux hosts (won't relabel `$HOME`) and the macOS Podman VM (can't traverse `~/.Trash`). So rather than error, `konrad scratch` (and the bare `konrad` TUI launched from `$HOME`) mints a fresh timestamped dir under `~/.local/state/konrad/scratch/<stamp>/` and binds *that*. Location is load-bearing: it **must sit under `$HOME`** (the macOS Podman VM only auto-shares `$HOME`; apple/container VirtioFS-remaps paths under `~/.local/state/konrad/`, same as the other stores — a host `/tmp` scratch could mount on neither), and living in konrad's own state dir means it's swept by the same retention prune as the logs and wiped by `konrad reset`. It's a plain workspace bind — no firewall or mount special-casing — and konrad creates only the empty container dir, never writing into it, so the "doesn't touch the workspace" invariant above still holds. `shell`/`run` keep the hard refusal (an automation path shouldn't silently invent a directory); the redirect is agent-TUI-only. `konrad open` reveals the newest scratch dir in the host file manager (`open`/`xdg-open`, host-side — the CLI runs on the host, so no sandbox involvement).
- **Retention is one shared window across konrad's growing state.** The log dir and the scratch workspaces are both pruned at launch by age (`KONRAD_RETENTION_DAYS`, default 30; `0` disables). Unified on purpose — but the scratch prune deletes *agent-written content*, not just logs, which is exactly why the off switch exists and why the prune runs *before* a fresh scratch dir is minted (the current session's dir is never a candidate).
- **Sessions are ephemeral.** opencode's `~/.local/share/opencode/` isn't bind-mounted — sessions, SQLite DB, and logs die with `--rm`. Durable task memory is `.agent/task.md`, not the session DB; collapsing the two parallel durability paths keeps the design coherent.
- **Secrets never touch the workspace** — `auth.json` lives only in the `konrad-secrets` named volume.
- **Logs land at a host XDG path** (`~/.local/state/konrad/log/`), bind-mounted narrowly so opencode keeps writing structured logs while the workspace stays pristine. No `konrad logs` subcommand — write to a documented path and trust `tail`/`grep`, like `npm`/`brew`.

| Mount | Purpose | Type |
|---|---|---|
| `konrad-secrets` ↔ `…/.opencode-secrets/` | `auth.json` | named volume |
| `konrad-cache` ↔ `…/.cache/opencode/` | regeneratable cache | named volume |
| `konrad-state` ↔ `…/.local/state/opencode/` | model choice, small UI state | named volume |
| `~/.local/state/konrad/log/` ↔ `…/opencode/log/` | opencode logs | host XDG bind |
| `~/.config/konrad/context/` ↔ `/context` | org/user reference material | host bind, read-only, when present |
| `<cwd>` ↔ `/workspace` | the user's project | workspace bind |
| `<cwd>/{.git,.vscode,.claude,.mcp.json,…}` ↔ same under `/workspace` | the workspace guard | read-only overlay, when present |

`--profile <name>` suffixes the state + cache volumes for throwaway self-test isolation; `konrad reset` wipes the volumes + log dir + scratch workspaces (not `context/` — that's user-managed material, like the config layers).

**The boundary also covers what the host later executes from the workspace — the workspace guard.** Network and filesystem reach aren't the whole threat: the agent has the workspace read-write, and the host runs code *from* it after the sandbox exits, with the user's full rights and no firewall in the way (deferred escape). `git status` runs `core.fsmonitor`, a fetch fires `reference-transaction`, a commit fires hooks, a trusted VS Code runs `.vscode` tasks, a devcontainer reopen runs `initializeCommand` on the host, Claude Code loads `.claude/` hooks and `.mcp.json`. So `podman_run` overlays each of `WORKSPACE_GUARD_ENTRIES` in [bin/konrad](bin/konrad) read-only (via `ro_bind`) on top of the writable workspace bind — the list follows Anthropic's [sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime) deny list, widened to whole entries. Three rules, each probe-verified, make it a boundary rather than a speed-bump. **(1) Top-level entries only, each overlaid whole:** a mountpoint can't be renamed or removed (`EBUSY`), but a directory that merely *contains* one can — so a `.git/config` or `.git/hooks` overlay is defeated by `mv .git x` plus a fresh `.git`, while a whole `.git` directly under the bind root can't be moved aside. The cost is that the agent can't commit (reads — `status`/`log`/`diff` — still work); the agent prompt already says "never commit unless asked", and `KONRAD_WORKSPACE_GUARD=0` is the per-run opt-out for when the user does ask. **(2) Existing, non-symlink entries only:** overlaying an absent path makes the engine create a mountpoint in the user's tree, breaking the rule that konrad doesn't touch the workspace at startup; a symlink would bind whatever it targets, possibly outside the workspace. **(3) apple/container guards directories only:** its binds reject a file source outright ("is not a directory" — the whole launch fails), so there `.mcp.json` and a `.git` *file* (worktree/submodule checkout) go unguarded. The documented residual is therefore: that apple/container file gap, entries created during the session (a `git init` in a non-repo folder, a new `.vscode/`), nested repositories below the top level, symlinked entries, and anything the user deliberately runs (a `Makefile`, `package.json` scripts) — review the diff before running agent-touched code.

**The `context/` mount is a reference *substrate*, not a config layer.** A sibling of `org/`/`user/` under `~/.config/konrad/`, bound read-only at `/context` (named corpora in subdirs, `/context/<name>`) so the agent can `rg` org/user-supplied material — a host-mirrored wiki, internal docs — with no network and no stored secret. It carries none of the five opencode pieces and takes no part in the merge; accordingly it's bound only when the dir exists, and it's **agent-only** — in `home_mounts`, never `cfg_mounts`, because the firewall proxy consumes `cfg_mounts` to derive the allow-list and has no business seeing reference material. A bind (not a baked-in skill) is the right primitive because a corpus is large, churny (re-synced host-side, out of band), and zero-copy — a mount stays fresh for free. Activation layers on top, matched to how hard the agent should reach for a corpus: passive (the `environment.md` `/context` hint), described (an org/user `AGENTS.md` naming the corpus), or active (a *thin* org skill that **points at** the mount — never one that *contains* the corpus; that's the anti-pattern). If a corpus ever outgrows `grep`, the named escalation is an MCP retrieval sidecar — deliberately out of scope, since local grep over a bind is the lightweight, composed answer. Mount *presence* is also the boundary the opt-in confidential tier (ROADMAP) builds on — "don't mount the dir" is a cooperation-free seal in a way "don't load a skill" is not.

**Resource caps are default-on and auto-scaled to the host, identical on both engines.** Every agent launch runs with a `--memory` / `--cpus` ceiling; when unset, the default derives from the machine's own totals — half the host RAM (clamped to `2G`–`8G`) and all but two of the cores (clamped to `2`–`8`) — via `host_mem_mib` / `default_memory` / `default_cpus` in [bin/konrad](bin/konrad) (Linux `/proc` + macOS `sysctl`, fixed `4G`/`4` fallback). The ceilings are deliberately modest rather than an unbounded grab: docling fits comfortably in both, so a bigger machine keeps its headroom for a co-resident local model instead of konrad claiming most of the box. (They differ in force: RAM is a hard allocation — over-commit means an OOM kill — while `--cpus` is a time-shared quota that only bounds konrad's share during a simultaneous burst.) The default does double duty: it lifts Apple `container`'s 1G per-VM default — too small for the bundled docling models, which the kernel OOM-kills mid-run — *and* bounds runaway/fork-bomb usage on otherwise-uncapped Podman. Both CLIs accept the same flag spelling, so this needs no `eng_*` wrapper; `KONRAD_MEMORY`/`KONRAD_CPUS` pin explicit values, `0` disables a cap. The CPU cap is also exported as `OMP_NUM_THREADS` (floored to an integer; the host core count when the cap is off): docling/torch otherwise self-throttle to a 4-thread default no matter how many cores the cgroup allows, so the two halves ship together. (GPU acceleration is moot: torch is the `+cpu` build and the engines run a Linux guest, so neither CUDA nor Apple MPS is reachable.) On the shared-kernel Podman path the agent and proxy are further hardened — every Linux capability dropped (`--cap-drop=ALL`), `no-new-privileges`, and a task-count ceiling (`--pids-limit`, default `1024`, `KONRAD_PIDS_LIMIT` overrides) that bounds a fork bomb below the host's PID max; apple/container already bounds these at its per-container VM boundary. (A read-only root filesystem is still on the [ROADMAP.md](ROADMAP.md).)

### Egress firewall

**The agent has no direct route to the internet; a sidecar proxy is the only way out, and it forwards only an allow-list.** This closes the network as an exfiltration channel — a prompt-injected agent can't ship the workspace or the provider credentials to an arbitrary host.

- **Two networks, per run.** `bin/konrad` creates an `--internal` network (no route out) and a normal egress network. The agent joins *only* the internal one; the proxy joins both. So the boundary is enforced by the engine's networking, not by the agent's cooperation — the agent (uid 1000) can't reconfigure it. A Podman *pod* can't do this: pod members share one netns, so they'd share the same egress. Separate containers on separate networks is what isolates them.
- **Same topology on both engines (Podman and apple/container), but the apple/container plumbing is fussier** — all of it behind the `eng_*` wrappers, `fw_proxy_url()`, and `fw_setup()`. The deltas, each verified on macOS 26:
  - *Agent → proxy by IP, not hostname.* Podman serves the proxy's container name over its internal DNS even on an `--internal` net; apple/container has no resolver on a custom net, so the agent is handed the proxy's literal internal-net IP (re-read each run — it changes on recreate).
  - *Proxy egress leg is the built-in `default` net.* A `container network create` network on apple/container has **no DNS resolver and no NAT** — only the engine-managed `default` net resolves and reaches the internet. So the proxy is dual-homed on the custom internal net (to face the agent) **plus `default`** (to get out); Podman keeps a dedicated, torn-down egress net since every netavark network resolves+NATs.
  - *Attach order is load-bearing.* A container inherits its resolver from the **first** `--network`; an `--internal` net contributes none, so `default` must be listed **first** or DNS dies even though it's attached. The agent stays internal-only on purpose — it never resolves anything (it only ever talks to the proxy by IP).
  - The security property is identical to Podman's: enforcement lives in a container the agent can't reach, surviving a root-level agent compromise.
  - **Host-gateway seal (apple/container only).** apple/container's `--internal` net is *host-only*: its vmnet gateway sits on the Mac, so a host service bound to `0.0.0.0` would be reachable **directly** from the agent at the gateway IP, bypassing the proxy and the allow-list (rootless Podman has no such route — a container on a podman `--internal` net gets *network unreachable* to the host, verified macOS + Linux). konrad seals it: on the apple/container firewall path `bin/konrad` starts the agent as root with `CAP_NET_ADMIN` and hands its entrypoint the internal-net gateway, which the root prelude `ip route add blackhole`s before dropping to the unprivileged `node` user with the capability stripped (shared `exec_as_node` in [image/konrad-privdrop.sh](image/konrad-privdrop.sh)). The blackhole is kernel state the dropped agent can't remove, so the agent ends up both sealed and capability-less — and apple/container reaches **parity with Podman**: the only remaining path to the host is back through the proxy, at the allow-listed `host.containers.internal`. The seal is **fail-closed** — if the gateway can't be read or the route won't install, the run aborts rather than expose the leak (`--no-firewall` or `KONRAD_ENGINE=podman` knowingly opt out).
  - **Local-model host alias (apple/container only).** Sealing the direct path means local models route through the proxy like any other allow-listed host — exactly as on Podman. The one missing piece is name resolution: Podman injects `host.containers.internal` into the proxy's `/etc/hosts` for free; apple/container injects no such alias and has no `--add-host`, so `bin/konrad` hands the proxy the egress (`default`) net's gateway — the Mac host — and the proxy's root prelude (the same `konrad-entrypoint` block, keyed on `KONRAD_HOST_ALIAS_IP`) writes that mapping into `/etc/hosts` before dropping to `node`. `host.containers.internal` is in the baked allow-list floor, so a model request the agent forwards through the proxy reaches the host; any *other* host name or raw gateway IP stays default-denied.
- **A forward proxy, on purpose.** The agent gets `HTTP(S)_PROXY` pointed at the sidecar. opencode runs on Bun, which honours those env vars for `fetch`; this was verified end-to-end (its HTTPS model-catalog `CONNECT` and local-model HTTP calls both route through). A forward proxy keeps the agent capability-less — no `NET_ADMIN`, no nftables, no transparent-interception machinery. The proxy is [tinyproxy](https://tinyproxy.github.io/) (`apt`-installed into the one image, not a second artifact to pin/pull) with `FilterDefaultDeny` + an anchored host filter.
- **The allow-list is derived, not hand-maintained.** The proxy runs the *same* `merge-config.js` over the *same* baked < org < user layers the agent sees and extracts every `provider.*.options.baseURL` host. opencode's *built-in* providers carry no `baseURL` (you enable them with just a key or `/connect`; opencode resolves their endpoint from the SDK / models.dev), so for those the proxy resolves each provider the user has **connected** (`auth.json` — read-only, ids only, never the keys) or **declared** (a `provider` block / a `model` prefix) to a host through a baked `provider-id → host` map ([image/konrad-defaults/provider-hosts.json](image/konrad-defaults/provider-hosts.json), generated from models.dev by [scripts/resolve-provider-hosts.sh](scripts/resolve-provider-hosts.sh) and refreshed by the daily lock bot — the same "pin upstream data, bake the pinned copy" pattern as `image/locks/`). So it tracks the user's real providers automatically, whether declared in config or picked interactively. Unioned with a deliberately tiny baked floor — `host.containers.internal` (local models) and `registry.npmjs.org` (the on-demand provider SDK adapters opencode isn't already bundling) — plus the org/user `allowed_hosts` files (+ `--allow-host` for a run). The floor was trimmed empirically: a configured model resolves and runs without `models.dev`, and OpenAI-compatible providers need no npm fetch, so `models.dev`/PyPI/the open web are opt-in, not default. Running the proxy *from konrad's own image* is what makes the derivation free — a stock proxy image would have neither the merge tool nor the config layers. Host-based filtering (not IP) is deliberate: remote providers sit behind rotating cloud IPs. The derivation itself lives in **one baked script** ([image/konrad-defaults/compose-allowed-hosts.sh](image/konrad-defaults/compose-allowed-hosts.sh)) so it can't drift between consumers: the proxy anchors its output into the tinyproxy filter, and [image/entrypoint.sh](image/entrypoint.sh) inlines the *same* list into the agent's `instructions` at session start — so the model knows which hosts a fetch can reach instead of burning turns on ones the proxy will refuse. The proxy stays the enforcing boundary; the inlined copy is a start-of-session hint (it doesn't follow a mid-session `/connect` — the proxy's live-reload does — and it's only emitted when the firewall is on).
- **Live-reload, so connecting a provider needs no restart.** The filter isn't frozen at proxy start: the sidecar polls `auth.json` and, on change, rewrites the filter and signals tinyproxy (`SIGUSR1` — reloads the filter list without dropping active connections). So an in-session `/connect` of an API-key provider takes effect within seconds, no relaunch and no `--no-firewall`. The one exception is an *OAuth* first-connect (Claude Pro/Max, Copilot): that handshake needs the host *before* `auth.json` exists, so a mid-session connect can't auto-allow it. The clean path is **`konrad connect`** (`do_connect` in [bin/konrad](bin/konrad)) — it runs `opencode auth login` with the firewall **off**, which is safe precisely because no agent is in the loop (pure authentication, no prompt-injection surface), so OAuth and API-key logins alike need no flags. A one-time `--allow-host`/`--no-firewall` remains the escape hatch for connecting *inside* a normal session.
- **Default-on, with a clean bypass.** On for every `run`/`shell`/`run`-oneshot launch; `--no-firewall` (or `KONRAD_FIREWALL=0`) restores the pre-firewall unrestricted path (a bare `exec podman run`). The proxy + networks are per-run (`$$`-named) and torn down by an EXIT trap. Mechanism lives in [image/konrad-proxy-entrypoint.sh](image/konrad-proxy-entrypoint.sh) and `fw_setup`/`fw_teardown` in [bin/konrad](bin/konrad).

## konrad code

**A second mode on the same CLI, engine and image, with the opposite trade-off: an agent gets your data or the internet, never both.** `konrad` sees the user's files and context, so its egress is sealed to an allow-list. `konrad code <git-url>` runs a third-party coding agent (Claude Code first) on a repo that already lives on the forge, so its egress can be open. It replaced konrad's own dev container as the place to run a coding agent in bypass mode: a dev container is porous by construction (attached-IDE sockets, the host podman socket, a bind-mounted workspace whose files the host later executes), and Docker Sandboxes' license rules out commercial use.

- **Nothing the agent writes reaches the host.** `do_code` in [bin/konrad](bin/konrad) passes only the URL string (plus the user's git name/email, for attribution) into the container; there's no workspace bind, none of `konrad`'s config layers, no `context/`. That removes the deferred-escape surface the [workspace guard](#state-secrets--isolation) can only narrow: nothing the agent writes ever lands where the host runs it. The one host mount is the user's own code layer, below — read-only, so the guarantee holds. Three named volumes carry the state (a fourth, the image store, under `--nested`; `--profile` suffixes all of them, login included — unlike `konrad`'s profiles, which keep credentials shared — so a first run can be rehearsed in isolation): `konrad-code-<host>-<path>` (the clone and its token, per repo), `konrad-code-tools` (`~/.local`: the agent binary) and `konrad-code-config` (`~/.config`: its login and settings). The mountpoints already exist node-owned in the image, so a fresh volume inherits that ownership even though the container starts as root (no `:U`, which would chown to the start user); `:nocopy` keeps Podman from seeding the config volume with opencode's baked config.
- **The user's code layer is a read-only bind, not a copy.** `~/.config/konrad/code/user/` mirrors `~/.claude` for the coding agent (`CLAUDE.md`, `skills/`, `agents/`, `commands/`, `rules/`), a separate tree from `konrad`'s `org/`/`user/` because a coding agent and the coworking agent want different instructions. `code_user_layer` binds it read-only at `/opt/konrad-code/user` when it exists — outside the volumes, so no stray mountpoint lands in one — and the entrypoint links its pieces into `$CLAUDE_CONFIG_DIR` under the same paths — `CLAUDE.md` itself, the four folders one entry at a time, because Claude writes into them too (`skills/synced/`, the account's synced skills) and a read-only folder link would break that — replacing an entry of the same name in the volume: the layer is the one home for user-level config, so there's nothing in the volume to preserve or merge with (a user `CLAUDE.md` kept there was never a documented path, can't be seen or versioned from the host, and per-repo config volumes would make it per repo anyway). Each start first drops the links the last one made (`find -lname '/opt/konrad-code/user/*'`), so whatever left the layer is gone from the session too. Claude Code follows all five kinds of link, a skill's scripts included (probe-verified, 2.1.292). `CLAUDE.md` rather than the tool-neutral `AGENTS.md`: Claude Code has no user-level `AGENTS.md` slot, and the folders are Claude Code formats anyway, so the layer is Claude-shaped as a whole. Copying the content in through an environment variable was weighed and dropped: it keeps "nothing mounted" literally true but caps out near 128 KB per value, which skills with scripts and assets outgrow, while a read-only bind carries a whole dir as is and stays live. Read-only keeps the real guarantee, since the agent can't make a locked read-only bind writable, not even from a nested user namespace. What the bind costs instead is guarded host-side: the session has open egress, so whatever the dir holds can leak, and a *symlinked* dir would bind its target (a convenience link to `~/.claude` would hand over credentials and transcripts), so it's refused; symlinks inside it resolve in the container and dangle, and without a keep-id user namespace node reads the files as "other", so both are flagged with a warning. Unprobed: the confined `--nested` label (`container_engine_t`) reading the host dir on an SELinux host (`konrad`'s own config binds work unrelabelled under `container_t`).
- **Git is the only way back.** A per-project access token (role Developer, typed inside the container on first run, stored in the repo's volume via git's `store` helper) plus a protected `main` means the agent can push a branch and open a merge request (`git push -o merge_request.create`) and nothing more. The user reviews on the forge, CI runs on the runners, the user merges, and code reaches the host only through their own `git pull`. The first run clones; later runs only `git fetch`, never touching a working tree that may hold unpushed work. Every token expires, and on a public repo a dead one would only surface when the agent's push fails, so each run asks GitLab's token self-lookup (`/api/v4/personal_access_tokens/self`, valid for project tokens) about it: a 401 re-asks, a missing `write_repository` scope or an expiry within 14 days warns, anything else (another forge, no network) skips — the one GitLab-specific call, best-effort by design.
- **The seal is IP-level, in the agent's own netns, not a proxy.** tinyproxy filters on the *requested hostname*, so with open egress any name that resolves to a private address (or a raw IP) would reach the LAN or host through it. So [konrad-code-entrypoint.sh](image/konrad-code-entrypoint.sh) starts as root, installs `unreachable` routes for private, CGNAT, link-local, multicast and reserved space (v4 and v6) plus the container's own connected subnets into a dedicated table, and adds a policy rule that consults it *before* `main` — so it beats even the connected route to the gateway. The one exemption is port-scoped: DNS (53/udp+tcp) to the resolvers in `resolv.conf`, which sit in private space on every engine (gvproxy, pasta, apple/container's gateway). It has to be port-scoped because gvproxy serves its port-forwarding API on port 80 of the same address; probe-verified that an unsealed container reaches that API and a sealed one doesn't. The host's own interface networks (address/prefix only, read host-side by `host_ip_cidrs`) are added to the same table, so a LAN on public addresses — where the host would otherwise be reachable at its own IP — is sealed too. On Podman the run pins `--network bridge` and sets `rp_filter=0` on the container's interfaces: netavark sets loose reverse-path filtering on `eth0`, and with private space `unreachable` it dropped inbound packets mid-transfer (sealed clones stalled 3/3; 2/2 passed with it off; `/proc/sys` is read-only inside, so it has to be a `--sysctl`; apple/container downloads don't stall without it, probe-verified). Public DNS instead of the engine's resolver was tried and dropped: networks that block outbound UDP 53 (verified on such a network) break it. The entrypoint then drops to node via the shared `exec_as_node` with the bounding set cleared, so the rules are kernel state the agent can't remove — the same trust model as the apple/container host-gateway seal, and fail-closed the same way (a failed route/rule or a routable private self-check address aborts the run). Consequences: no sidecar, no extra networks, and it covers every protocol (git over ssh, raw sockets), not just what honours `HTTPS_PROXY`. On Podman the start keeps only `NET_ADMIN` (routes), `SETUID`/`SETGID` (the drop) and `SETPCAP` (clearing the bounding set), with `no-new-privileges` and the pids cap.
- **The agent binary is installed on first use, never shipped.** Its license lets a user install it but not konrad redistribute it, so the image carries none: on the first run the entrypoint asks, then runs the vendor's official installer (`curl -fsSL https://claude.ai/install.sh | bash`) into the shared tools volume, where the agent also self-updates. That installer downloads a ~240 MB binary with a silent, timeout-less `curl`, so a stalled network would read as a hang; the entrypoint hands it a `CURL_HOME/.curlrc` (abort under 1 KB/s for 60 s) and watches the download file for a progress line — the vendor's script runs unmodified. Logging in once inside the container (a URL to open, a code to paste back) persists in the config volume (`CLAUDE_CONFIG_DIR` points there), so subscription logins work, not just API keys. The session is `claude --dangerously-skip-permissions` in the terminal, no IDE attached, with a short `--append-system-prompt` note carrying the two facts the agent can't discover itself (the git-only way back, the sealed LAN) — konrad's own prompts and skills don't apply here.
- **Nested containers are rootless, opt-in, and never touch the seal.** `konrad code --nested` gives the agent rootless Podman (baked into the image; see the nested-Podman block in [image/Dockerfile](image/Dockerfile)). Rootful nesting is out: it needs `NET_ADMIN` on the agent, which deletes the seal. Rootless keeps it: nested capabilities live in a user namespace the agent creates, which never owns the agent's netns, and nested containers (pasta, `--network host`, a nested bridge) egress through that same sealed netns — probe-verified, along with seal-removal attempts from node, from userns-root and from a nested `--privileged` container ([scripts/probe-nested.sh](scripts/probe-nested.sh), baseline included). What it takes, each piece probe-forced: `newuidmap`/`newgidmap` with *file capabilities* rather than Debian's setuid bit (the setuid binary opens `uid_map` as a non-owner, which the kernel refuses); so `no-new-privileges` goes for the run and `exec_as_node --keep-caps setuid,setgid` leaves exactly those two in node's bounding set (stage 2 fails closed on anything else); every other setuid bit is stripped from the image, and the mappers are inert on every other run, because `no-new-privileges` and the cleared bounding set both void file capabilities. A real subordinate range (`node:1:999` + `node:1001:64535`, inside 0..65535 so it exists under a rootless outer engine too; single-uid mapping can't build images that `chown`). On Podman, `SYS_CHROOT` (its seccomp allows `chroot` only with it), `/dev/net/tun`, `unmask=ALL` (the kernel refuses a nested `/proc` mount while any of it is masked, and the nested crun masks the same `/sys` paths again, which SELinux refuses on top of the outer masks' tmpfs) and `label=type:container_engine_t`; `containers.conf` drops default sysctls (read-only `/proc/sys`) and shares the UTS namespace (seccomp refuses `sethostname`). apple/container has no such flags, so the root prelude gets `SYS_ADMIN` for itself (the drop clears it) to open tun and unmount the masks. The store is a per-repo volume at `/var/lib/konrad-containers` (outside `~/.local`, the tools volume; native overlay can't stack on the overlay rootfs), so builds stay warm (konrad's own: ~2 min cold, under 10 s warm) and one repo's images can't poison another's; on apple/container it's an engine volume, not a host dir like the other stores, since VirtioFS refuses both the `chown` and the overlay's pivot dir. **SELinux stays on, as `container_engine_t`** — container-selinux's type for engines inside containers. `container_t` refuses the nested `/proc` mount and the tun device, and `label=nested` keeps `container_t`; `label=disable` ran the agent `spc_t`, which on native Linux meant a simulated escape (as the agent's host uid, Fedora, enforcing) read a world-readable `/tmp` file, `/etc/passwd` and the system D-Bus, exactly as with no SELinux, where `container_t` is denied all three. `container_engine_t` keeps `container_t`'s wall towards the host: diffing the two in the Fedora 44 policy (attributes expanded), every permission it adds on a type outside the container is a mount operation (`mount`, `remount`, `mounton`, which the kernel still limits to userns-mountable filesystems) or fuse/devpts device use — no `read`, `open`, `write` or `connectto` on host files, `/tmp`, home or the D-Bus daemon. On top come rights over its own `container_file_t` (manage, relabel), `cgroup` writes and unconditional kernel module auto-loading (`module_request`, boolean-gated for `container_t`). Probed on the host kernel and policy (2026-10-01) by switching a process's type: pasta, nested bridge and host networking, a build with cache and secret mounts, volumes, `keep-id` and the seal itself all work under it; nested containers inherit the type, since the nested Podman sees SELinux as disabled. The type may only be entered from container files, so PID 1 is the image's own `catatonit` rather than the host binary the engine's `--init` mounts (which it refuses: `exec container process /run/podman-init: Permission denied`). Both start-path findings came from the maintainer's first real labelled launches; switching a running process's type had missed them. One catch: a store an unconfined run filled carries the `unconfined_u` SELinux user, and the confined agent (`system_u`) can neither copy up its directories (overlayfs creates them with the lower layer's label, which a user change makes a denied create) nor relabel them, so every nested container fails to start (`crun: open …/merged/…: No such file or directory`). The entrypoint resets such a store once — it's a cache. The probe's delta against today's flags is the reason it's opt-in: on apple/container (a VM per container, no seccomp/SELinux to lose) only the `/proc` masks, tun and a `/proc` mount inside a userns change; on Podman also `no-new-privileges` and `SYS_CHROOT` (ROADMAP: whether to nest by default). User namespaces themselves are allowed without `--nested` already.
- **Parallel sessions are git worktrees of the one clone.** With the merge-request workflow, agents no longer need a shared working tree — only a shared forge — so a second `konrad code` on the same repo gets its own worktree (`/workspace/.sessions/<name>`) beside the clone, which stays the `primary` session's, unchanged from before. Worktrees rather than a volume per session: they share the clone's objects and token (one fetch, one token per repo), and git refuses to check out one branch in two of them, the guard parallel agents need. `do_code` picks the session host-side, from container names (`konrad-code-<pid>-<repo id>-<session>`, the repo id a checksum of the repo volume's name): the pid keeps `sweep_orphans` working, and names rather than labels because the engine listing it already reads covers both engines — a lock file inside the volume wouldn't, since apple/container runs each session in its own VM. Without `--session` a run takes the clone while it's free, else the lowest free `s<n>`; a live name is refused. Under `--nested` the image store stays shared, but libpod's database is per session: it lives in the store (`static_dir`), while its run state and lock table live in each container's `/tmp` and `/dev/shm`, so two sessions on one database reset each other's running containers (a fresh `/tmp` looks like a reboot to libpod) and hand out the same locks — probe-verified with a baseline, [scripts/probe-shared-store.sh](scripts/probe-shared-store.sh). A non-primary session points `static_dir` and `volume_path` at `sessions/<name>/` in the store (a `CONTAINERS_CONF_OVERRIDE` file), images and layers stay shared and file-locked; the primary keeps libpod's default, so existing stores carry on. On apple/container the store is a block volume one VM can attach, so a non-primary session there gets a store volume of its own.
- **Accepted residuals.** Open egress means the repo and the token can leak (fine for one's own code with a single-project, revocable token; not for repos containing secrets). The tools and config volumes are shared across repos, so a compromised session could tamper with them for the next repo's session (per-repo isolation of those volumes is the fix if that matters). Parallel sessions on one repo share its volume and, under `--nested`, its images, so they're one trust domain: a compromised session can reach its siblings' worktrees and images. "LAN" is private address space, the connected subnet and the host's own networks; anything else on public addresses is internet. The image is the full konrad image with a different entrypoint (git, uv, Python, Node already there); a slim dedicated image only if its size gets in the way.
- **konrad's own repo has no dev container, deliberately.** A dev container earns its keep by pinning a toolchain that's hard to install, by making onboarding one click, and by enabling hosted environments like Codespaces. None applies here: the static gates fetch every linter at a pinned version through `uv`/`npx` ([scripts/check.sh](scripts/check.sh), the same script CI runs), so the host toolchain is `uv`, `node`, `git` and the Podman a contributor needs anyway; that Podman is the real dependency, since the work is building and testing an image, and a dev container can't remove it (driving it from inside one took a host-socket mount plus a remote-daemon mode in `bin/konrad` that mapped every bind source back to a host path, rootful uid maps on macOS and a smoke-test skip, all of it code that existed for one environment); and the forge is GitLab. The container-shaped need, the agent's toolset with nothing on the host, is `konrad code --shell --nested`, which is the agent's real environment rather than a hand-kept copy of it; editor comfort is a committed `.vscode/` with recommended extensions. Revisit if outside contributors become regular (then an edit-and-lint-only `devcontainer.json` on a stock image, no socket), or the repo gains a native toolchain worth pinning.

## The planning contract

Two **independent** gates, baked into the agent prompt ([image/opencode/agents/konrad.md](image/opencode/agents/konrad.md)):

- **`.agent/task.md`** — when the task has *side effects* (file edits, state-changing commands). A binary check at first tool-selection, not a complexity prediction. The agent writes it *before* the first side-effecting call, in a fixed shape:

```markdown
# <task title>
## Understanding       — what the user wants, as I read it
## Plan                — 3–5 bullets (the path, not micro-steps)
## Success looks like  — how I'll know I'm done
## Decisions & findings — appended during execution
## Outcome             — what shipped, what didn't, caveats
```

- **`todowrite`** — for anything beyond a trivial single Q&A; opencode's live in-UI checklist.

`task.md` holds *what & why* (durable, survives context compaction); `todowrite` holds *where the agent is right now*. No overlap, no sync burden. The agent surfaces the plan inline and proceeds when confident, or asks via `question` when a wrong guess would be costly (ambiguous goal, irreversible step). The `quality-assurance` skill later reads `task.md`'s Plan + Success + Outcome to render its verdict.

## Build & reproducibility

**Every input is locked; a bot maintains the locks; the publish is smoke-gated.**

- Each input is digest- or version-locked in [image/locks/](image/locks/): base image, the `uv` source image, Python deps (`python.lock`), `opencode-ai`, `typst`, and the Docling model repos (`models.lock` — commit-pinned so the ~1.1 GB model layer stays byte-stable across rebuilds; one `COPY` layer per model means a single-model update re-pulls only that model, not the whole set). apt packages float — they refresh whenever the base image bumps. The [image/Dockerfile](image/Dockerfile) top comment mirrors this list.
- The Python venv ships as **three `COPY` layers** (the `venv-split` build stage partitions it): torch (~700 MB), the large slow-moving numeric wheels (opencv/scipy/numpy/onnxruntime/sympy, ~450 MB), and the churny remainder (~360 MB). So a `python.lock` bump that only moves a small pure-python dep — the near-daily case, since the bot tracks every transitive — re-pulls just the light layer, while torch and the numeric set dedupe (same byte-stability mechanism as the per-model split above). Sibling to the model-layer dedupe.
- The GitLab `resolve-locks` bot re-resolves each upstream daily and opens an auto-merging MR **only when something moved** — so a rebuild fires only when there's genuinely something new. No scheduled cron rebuild. (The build-side of the low-maintenance ethos: freshness is a bot plus upstream registries, not hand-tended bumps.)
- **Reproducible layers** — CI builds with `SOURCE_DATE_EPOCH=0` + `rewrite-timestamp=true`, so byte-identical content yields byte-identical layer digests; that's what lets users skip a re-download when nothing actually changed. Local `konrad-dev rebuild` writes `konrad:local`, separate from the published `:latest`.
- **CI runs on a GitHub mirror; the primary repo stays on `gitlab.git.nrw`** (one-way push mirror → GitHub Actions does build → smoke → publish to `ghcr.io/jlbauss/konrad`). Why: gitlab.git.nrw's shared runners can't run the privileged Podman build. The GitHub side is public for discoverability but takes no contributions — CI plus auto-mirrored releases only; issues and MRs live on GitLab. (Full contributor + release flow: [CONTRIBUTING.md](CONTRIBUTING.md).)
- Every image carries `/etc/konrad/build-manifest.json` (dpkg / npm / pip versions + build metadata); `diff` two `:<short-sha>` images' manifests to bisect a regression to its upstream cause.

## Distribution & updates

**konrad ships as two artifacts that version and update on independent channels**, and conflating them is the trap this design avoids. The **CLI** (`bin/konrad`, a bash script) and the **image** (the canonical artifact, pulled from GHCR) drift by design — a CLI-only patch bumps `VERSION` without firing an image rebuild (the workflow's `image/**` paths filter), so `konrad --version` prints both.

- **The CLI updates through its install channel.** `curl|sh` today; a GitLab-hosted Homebrew tap is on the [ROADMAP.md](ROADMAP.md). konrad never self-updates the CLI from a *background* process — rewriting the running script mid-flight is a footgun, and the install channel is the honest owner of the binary anyway. `konrad update` on a `curl|sh` install re-runs the installer to refresh the CLI in-place; a symlink (dev) install is left to `git pull`.
- **The image (and org layers) stay fresh via a throttled background refresh** — this is the piece an install channel can't provide, since neither `curl|sh` nor Homebrew can touch a ~1 GB GHCR image. Every launching verb calls `maybe_background_refresh` ([bin/konrad](bin/konrad)): at most once per `KONRAD_REFRESH_INTERVAL` (default daily), it fires a **detached** worker that pulls `:latest`, re-tags the local `konrad:latest`, and runs `org_sync_all`. The launch never waits on it and never fails because of it; the current run uses whatever image it already has, and the *next* launch picks up a newer one — announced by a one-line note (the worker writes it only when the pulled image's **content ID** actually changed, so a lock-only rebuild that doesn't move `VERSION` is still caught, and an unchanged pull stays silent).
- **Availability beats freshness, deliberately.** The throttle stamp is written *before* the worker runs, so a failed or slow refresh (offline, registry down) still counts against the interval rather than retrying every launch — the same principle as an org sync keeping its last-good checkout. The escape hatch is `konrad update`, which does the identical refresh **synchronously and now**, plus the CLI. Worker output goes to `~/.local/state/konrad/refresh.log`, never the terminal.
- **Org `hooks/post-sync` runs unwatched — and the notice queue is how its news gets back to the member.** Because org sync rides the background worker, a subscribed layer's host-side `post-sync` hook fires detached at the refresh cadence, its raw output going to the refresh log rather than in front of the user. The **notice queue** closes the visibility gap the detached worker opened: a stateless, drained "news" channel from a prior worker (image-update announcements, refresh faults) *or* an org hook (via `KONRAD_NOTICE_DIR`) to the next foreground launch. The worker/hook writes one `key: value` file per notice under `~/.local/state/konrad/notices/`; `launch_preflight` renders and deletes them (`notices_flush` in [bin/konrad](bin/konrad)). Design choices, each load-bearing: **stateless** — a notice is rendered then dropped, and the next refresh re-creates it while the fault persists, so a fixed fault stops regenerating and its notice disappears with nothing to acknowledge, migrate, or get stuck; **source by path, not by field** — a top-level file is `konrad`'s, an `org-<name>/` subdir is that layer's, so a hook can't forge konrad-branded text (and its lines are sanitized + capped on render); **a severity ladder that never breaks the launch** — `info` is one dim line, `warn` a framed block, `blocked` adds an Enter-to-continue but *only* on an interactive stdin (never under a piped `konrad run`, `KONRAD_NO_NOTICES=1`, or a disabled refresh), honoring the "a launch never blocks" invariant. A non-zero hook that wrote no notice has its last output lines promoted into a `warn` attributed to the layer, so every existing layer gains visibility with no change on its side. The trust model is unchanged (subscribing is trusting; see [Configuration & instructions](#configuration--instructions)).

**The desktop launcher is generated on-machine, not shipped.** `konrad install-desktop` writes a user-scope launcher (a freedesktop `.desktop` + hicolor icon on Linux; a `~/Applications/Konrad.app` bundle on macOS) whose action is `konrad scratch` — a GUI launch has no project cwd, so the [ephemeral scratch workspace](#state-secrets--isolation) is exactly where it lands. Three design choices carry it: **(1)** every launcher points at one shared **wrapper script** (`~/.local/share/konrad/launch.sh`) that locates konrad (a GUI `PATH` often omits `~/.local/bin`), offers to `curl|sh`-install it if missing, then execs `konrad scratch` — so the behavior lives in one place, and it's the same wrapper the future MDM-distributable `.app` ([ROADMAP.md](ROADMAP.md)) will bundle. **(2)** The TUI needs a terminal a GUI click doesn't provide, so Linux leans on `.desktop` `Terminal=true` (spec-correct but DE-dependent — `install-desktop` warns when no terminal-launcher is found) and the macOS bundle's executable spawns one around the wrapper (Terminal.app by default; `KONRAD_TERMINAL` selects another — `ghostty`/`alacritty` via `open --args -e`, `iterm` via its own AppleScript — validated against LaunchServices at install, since macOS has no OS-level default-terminal setting to defer to). **(3)** The icon has **one source of truth** — the committed [`assets/konrad.svg`](assets/konrad.svg) — installed verbatim as the Linux scalable icon and rasterized (via the committed PNG master + the preinstalled `sips`/`iconutil`) into the mac `.icns`; `install-desktop` reads `assets/` from a clone and fetches it from the repo raw URL on a `curl|sh` install (offline → generic icon, launcher still works). It's the verb the other install channels *call* (the installer's opt-in prompt; the future Homebrew formula) rather than reimplement. This is host-side GUI integration only — no sandbox, engine, or image involvement, like `konrad open`.

**Because the launcher is generated, regenerating it is a real operation — and it has to be ask-free and choice-preserving.** The installer doubles as the CLI's update channel (`konrad update` re-runs it), so the launcher step is re-entered on *every* update, and treating each run as a first install broke twice over: it re-asked the opt-in question forever, and the natural "just hit Enter" answer regenerated an existing launcher from a bare environment, resetting a chosen `KONRAD_TERMINAL` back to Terminal.app. The fix splits creation from maintenance. **(a)** The ask is gated on a genuinely *fresh* install — the installer already computes that (a konrad on disk at the target is an upgrade) for its clobber check, so the discriminator is free and needs no new state; a decline is therefore permanent-by-default, with `konrad install-desktop` as the opt-in later. **(b)** An upgrade instead rides `install-desktop --refresh`: regenerate **only if a launcher is already installed**, else a silent no-op. That's what keeps generated code current (a wrapper fix has to reach launchers already on disk) without ever creating one the user declined. **(c)** The terminal choice is stored **in the launcher itself** — the generated bundle exec carries a `TERM_ID` line that `resolve_mac_terminal` reads back when `KONRAD_TERMINAL` is unset (explicit env > recorded > Terminal.app). The launcher *is* the state: nothing extra to write, migrate, or leave behind after `--remove`, and the read keys on a structural assignment we generate, never on the app's display name. A recorded value this konrad no longer supports (or whose app was since uninstalled) warns and falls back rather than aborting — it's not the user's typo to be blocked on, unlike a bad `KONRAD_TERMINAL`, which still fails loudly. **(d)** Regeneration is fail-safe on the icon: both back-ends build into a temp and only move it in on success, keeping the installed icon otherwise, because the asset fetch can fail offline and a refresh must never *downgrade* a working launcher.
