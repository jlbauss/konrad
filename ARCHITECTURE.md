## The big picture

konrad runs [opencode](https://github.com/sst/opencode) inside a sandboxed, rootless Podman container.

- **The image is the canonical artifact.** `image/Dockerfile` builds it; `bin/konrad` — a thin host-side bash CLI — is the primary consumer.
- **No IDE attaches to the sandbox — deliberately.** VS Code Dev Containers bridges every attached container to the host through sockets in `/tmp`: the host's `git credential` helper, the SSH agent, askpass, and the IPC channel, over which code in the container can install an extension that types commands into a *host* terminal. Microsoft treats this as by design, and no setting closes all of it, so attaching would carry a host channel *inside* the firewall boundary and void "can't touch anything outside the workspace."
- **Podman, not Docker.** Open-source, free for commercial use, ergonomic on macOS. `--userns=keep-id` shares the container `node` user's UID with the host user, so bind-mounted files have sane ownership. Docker isn't supported.
- **Two engines, one abstraction.** The supported platforms are Linux with Podman and Apple-Silicon macOS 26+ with Apple's [`container`](https://github.com/apple/container), which konrad always picks on macOS; there's no Podman fallback for other Macs, because testing every change on a third platform costs more than those Macs are worth. The two CLIs aren't subcommand-compatible, so every host-side engine call in `bin/konrad` goes through an `eng_*` wrapper and `detect_engine()` fixes the choice once at startup (`KONRAD_ENGINE` overrides). apple/container needs no `--userns` (VirtioFS maps guest UIDs → the host user) and rejects the `:z`/`:U`/`:ro` mount suffixes, so those are dropped there. Its named volumes are root-owned and can't be chowned, so the three persistent stores (secrets/cache/state) are host directories under `~/.local/state/konrad/store/`, which VirtioFS remaps to the container user like the `/workspace` bind. The remap is per lookup: VirtioFS reports a file as owned by whichever guest uid asked, briefly cached, so an ownership check can see root or a nested container's uid on a file node owns. Block-backed volumes would give real ownership but attach to one VM at a time, and `konrad code`'s config, tools and clone are shared across sessions and repos, so they stay on VirtioFS and the ownership-checking tools stand down instead: `konrad code` trusts the clone as a git `safe.directory` and sets `XDG_CONFIG_HOME` to its default, which podman then doesn't second-guess.
- **A wedged engine fails fast, not forever.** Short apple/container calls (status, network create and delete, container removal and the teardown) and org post-sync hooks run under `bounded`, the one shell watchdog in [bin/konrad](bin/konrad) (stock macOS has no GNU `timeout`); interactive runs don't, since they're meant to last. The case that made it necessary: apple/container's service keeps running from the install it started from, so after `brew upgrade container` deletes that install, every network and container start blocks. `container_service_check` reads `container system status` before a launch (server version ≠ client version, or the install root gone) and stops with the fix. It doesn't restart the service itself: a restart ends every running container, other konrad sessions and `konrad code up` repos included, and the fix is one command after an upgrade.
- **Tuned for Qwen3.6-class local models.** The agent prompt ([image/opencode/agents/konrad.md](image/opencode/agents/konrad.md)) is sized for a ~30B-class local model; the tested recommendation is `qwen/qwen3.6-27b`. Frontier models work fine; sub-10B ones may need prompt softening.

## Engineering ethos — lightweight, composed, low-maintenance

The guiding principle behind every other choice here: **konrad stays lightweight and leans on well-maintained building blocks rather than custom code.** Prefer configuring an existing tool over shipping bespoke machinery; drive ongoing maintenance toward zero, so konrad keeps working and current even through stretches when no one is actively developing it. (This is why model-discovery's custom plugin was dropped, the config deep-merge is a tiny self-contained step, and the whole pinning/rebuild story is a bot plus upstream registries.)

Its second face: **simple, logical, and smooth beats clever.** konrad should stay tidy and resist sprawl. A solution that *feels* surprising (e.g. the runtime user lacking write access everywhere in its own home) is a smell to fix at the structural cause, not a quirk to live with — today's quiet workaround is tomorrow's unexpected consequence. Accumulating complexity is debt to pay down deliberately; periodic cleanliness passes are part of the maintenance story.

## Configuration & instructions

Config is **layered, not replaced** — host-mergeable layers, folded left, last writer wins:

```text
baked image defaults   <   org layers (0..n)             <   user
/etc/konrad/…               ~/.config/konrad/org/<name>/      ~/.config/konrad/user/
```

- Each layer holds the same opencode pieces — `opencode.jsonc`, `agents/`, `skills/`, `instructions/`, `AGENTS.md`, `fonts/`. [image/entrypoint.sh](image/entrypoint.sh) composes the `opencode.jsonc` of each via [image/merge-config.js](image/merge-config.js) (an N-input deep-merge) before opencode loads anything. **Objects merge recursively; arrays replace** — which is why agent rules are added via `AGENTS.md` or `instructions/`, not by overriding the `instructions` array. (A layer may also carry an `allowed_hosts` file — konrad-specific, consumed by the egress firewall, *not* part of this merge.)
- **`org/` is a container of named layers, and a subscribed layer is a managed git mirror.** `konrad org add <git-url>` clones a repo to `org/<name>/`; `konrad org sync` (riding every `konrad update`) does `git fetch` + `reset --hard @{u}`. Local edits to tracked files are clobbered by design (the user's channel is `user/`, which always merges on top); a failed sync warns and keeps the last-good checkout (availability beats freshness for a defaults mechanism); and there's **no state file**, since the in-place `.git` records URL and branch. Layers fold in alphabetical name order (`10-`/`20-` prefixes steer precedence); a plain non-git dir is a manual layer that never syncs; a detached-HEAD checkout (a tag) is the pin. So an org ships updates by `git push`, with no bespoke updater and **no konrad auth code**: private repos work through the member's existing git credentials. The entrypoint, [compose-allowed-hosts.sh](image/konrad-defaults/compose-allowed-hosts.sh) and the overlay loops all walk the *same* sorted enumeration, so precedence can't drift between channels, and the firewall derivation sees **every** layer's providers (a missed layer would silently block that org's internal endpoint).
- **The `hooks/post-sync` hook is a deliberate exception to "agent code runs only in the sandbox."** A layer may ship an executable `hooks/post-sync`; konrad runs it host-side after `add` and after every successful sync (cwd = the layer dir). It covers the org needs plain config can't express (mirror a corpus into `context/`, derive per-member identity from the org's own forge auth), and it *rides the branch*, so it updates with the layer. Trust model: **subscribing is trusting** — no prompt, no flag; adding a layer is the decision to run its code. konrad gains no declarative corpus-sync engine.
  - **The hook environment is a small contract,** because the usual sync path is the unwatched background worker, where `echo` reaches no one. konrad exports `KONRAD_NOTICE_DIR` (where to drop notices, the layer's channel to its members; see [below](#distribution--updates)), `KONRAD_LAYER_NAME`, and `KONRAD_HOOK_INTERACTIVE` (`1` on `add`/`sync`/`update`, `0` under the worker, so a hook picks `echo` vs. a notice without sniffing the tty). The hook is time-bounded (`KONRAD_HOOK_TIMEOUT`, default 120 s, under `bounded`) so an unwatched hang can't live until reboot.
- **Discovery is a well-known `$HOME` folder** (`~/.config/konrad/{org,user}`), not an env var or system path — because apple/container's VirtioFS remap makes paths under `$HOME` readable as the container user, and a user-level default needs no root to install.
- **Every read-only host bind is relabelled on Podman (`ro_bind`: `:ro,z`).** A dir under `~/.config` keeps its home label (`config_home_t`) through a plain bind, and no container type may search it, so on an SELinux host the org, user, `context/` and code layers would be mounted but unreadable, and the entrypoints, which only take what `[[ -f ]]`/`[[ -d ]]` finds, would run without them. *Shared* (`z`), not private (`Z`): the agent, the firewall sidecar, `konrad code up` and parallel sessions bind the same dirs at once, each with its own MCS pair, and a private label would lock out all but the last. The content is meant for the agent anyway, so a label every container can read adds no exposure. Both entrypoints warn when a bound layer is unreadable.
- **`AGENTS.md` is the user's slot; `instructions` is konrad's.** opencode loads both, additively. The baked `opencode.jsonc` declares one glob for the baked `instructions/` dir and one for the user's, and opencode expands them itself (skipping absent paths, de-duplicating, preserving order). **Org layers can't get a glob of their own**: opencode globs only an entry's *basename* (the dirname is literal), so `org/*/instructions/*.md` could never match. Instead the entrypoint **copies** each layer's `instructions/*.md` (and a layer-root `AGENTS.md`) into the baked `instructions/` dir as `org-<name>-<file>`, where the baked glob finds them — the same mechanism as the generated allow-list file, and the array-replace footgun never bites because only the baked layer declares the `instructions` array. Precedence, all additive: `environment.md → org instructions → user instructions → user AGENTS.md → project AGENTS.md`.
- The org layer is **defaults, not enforcement**: files in the user's own home, so "add-only" describes merge precedence, not a permission lock.
- **Model discovery is an inline entrypoint probe, and there's no baked `model`.** Provider endpoints ship pre-wired with empty model lists; at session start [discover-models.sh](image/konrad-defaults/discover-models.sh) probes `<baseURL>/models` for every provider with an explicit `options.baseURL`, in parallel and bounded (`KONRAD_DISCOVERY_TIMEOUT`; `KONRAD_NO_DISCOVERY=1` opts out), drops embedding models, and merges the results *below* the composed config, so discovery fills the picker but a declared model still wins. Each model gets `limit.context` when the endpoint exposes a window (vLLM's `max_model_len`, llama.cpp's `meta.n_ctx`), because opencode's auto-compaction keys off it; the probe never *guesses* a window, since a wrong one mis-compacts. opencode requires both `limit` keys once the object exists, so a discovered `context` gets a derived `limit.output` of `context/6` (floor 2048, capped at the window): proportional, because opencode subtracts it from the context to size compaction *and* sends it as `max_tokens`. The probe runs as `node` in the sandbox and sends each provider key only to the endpoint opencode itself would call, **through the firewall proxy**, so the key invariant holds and authenticated remote endpoints are discovered too. It replaced an upstream discovery plugin that cost seconds per start and a fragile build-time dependency. When opencode gains native `/models` discovery ([opencode#27554](https://github.com/anomalyco/opencode/pull/27554)), the probe can go.
- **Tool permissions are sandbox-shaped and live once, globally.** The baseline `permission` block sits in [opencode-defaults.jsonc](image/konrad-defaults/opencode-defaults.jsonc) (top-level, so every agent inherits it); per-agent blocks carry **only deltas**. The model follows the boundary, not the action's scariness: the container is disposable and non-root, so the agent acts freely *inside* it (`allow`), `ask` is reserved for the one irreversible action on the user's real files (`rm -rf` in the `/workspace` bind), and `deny` covers the escape vectors — root (`sudo`), host container/cluster control (`podman`/`docker`/`kubectl`), and the secrets volume under `external_directory`. Network tools stay `allow` because the [egress firewall](#egress-firewall) is the real network boundary. Only `ask` interrupts, so prompts are rare by design. opencode applies the *last* matching rule, so each object lists its catch-all first and the exceptions after it, and a layer's added rule lands last and wins; smoke-test.sh proves the denies by calling the tools, which also catches an opencode release that renames a key. Subagents add `question: deny` (no user in their loop) and tighten `rm -rf` to `deny`; [manual-transformer](image/opencode/agents/manual-transformer.md) is the worked example.

## State, secrets & isolation

**`.agent/` belongs to the agent end-to-end; framework state lives elsewhere.**

```text
.agent/
  task.md                     # planning artifact (committable)
  artifacts/                  # durable mid-task outputs (committable)
  scratch/                    # agent scripts / probes
  quality-assurance/<stamp>/  # verification evidence on a fail
```

- **konrad doesn't touch the workspace at startup.** It neither creates the `.agent/` tree (the agent and the quality-assurance helper `mkdir -p` their own dirs on demand), nor prunes it, nor edits `.gitignore`, nor writes a session sidecar. A launch leaves a clean repo clean.
- **A no-project launch gets an ephemeral scratch workspace, not a refusal.** `$HOME` can't be the workspace — it hands the agent the whole home, and SELinux hosts refuse the bind outright. So `konrad scratch` (and the bare `konrad` TUI launched from `$HOME`) mints a fresh timestamped dir under `~/.local/state/konrad/scratch/<stamp>/` and binds *that*. It **must sit under `$HOME`**, where apple/container's VirtioFS remap applies (a host `/tmp` dir wouldn't be writable), and in konrad's own state dir it's swept by the retention prune and wiped by `konrad reset`. konrad creates only the empty dir, so "doesn't touch the workspace" still holds. `shell`/`run` keep the hard refusal (an automation path shouldn't silently invent a directory). `konrad open` reveals the newest scratch dir in the host file manager.
- **Retention is one shared window.** The log dir and the scratch workspaces are both pruned at launch by age (`KONRAD_RETENTION_DAYS`, default 30; `0` disables). The scratch prune deletes *agent-written content*, which is why the off switch exists and why the prune runs *before* a fresh scratch dir is minted.
- **Sessions are ephemeral.** opencode's `~/.local/share/opencode/` isn't bind-mounted — sessions, SQLite DB, and logs die with `--rm`. Durable task memory is `.agent/task.md`, not the session DB, so there's one durability path, not two.
- **Secrets never touch the workspace** — `auth.json` lives only in the `konrad-secrets` named volume.
- **Logs land at a host XDG path** (`~/.local/state/konrad/log/`), bind-mounted narrowly so opencode keeps writing structured logs while the workspace stays pristine. No `konrad logs` subcommand — a documented path plus `tail`/`grep`, like `npm`/`brew`.

| Mount | Purpose | Type |
|---|---|---|
| `konrad-secrets` ↔ `…/.opencode-secrets/` | `auth.json` | named volume |
| `konrad-cache` ↔ `…/.cache/opencode/` | regeneratable cache | named volume |
| `konrad-state` ↔ `…/.local/state/opencode/` | model choice, small UI state | named volume |
| `~/.local/state/konrad/log/` ↔ `…/opencode/log/` | opencode logs | host XDG bind |
| `~/.config/konrad/context/` ↔ `/context` | org/user reference material | host bind, read-only, when present |
| `<cwd>` ↔ `/workspace` | the user's project | workspace bind |
| `<cwd>/{.git,.vscode,.claude,.mcp.json,…}` ↔ same under `/workspace` | the workspace guard | read-only overlay, when present |

`--profile <name>` suffixes the state + cache volumes for throwaway self-test isolation; `konrad reset` wipes the volumes + log dir + scratch workspaces (not `context/`, which is user-managed like the config layers).

**The boundary also covers what the host later executes from the workspace — the workspace guard.** The agent has the workspace read-write, and the host runs code *from* it after the sandbox exits, with the user's full rights and no firewall (deferred escape): `git status` runs `core.fsmonitor`, a fetch fires `reference-transaction`, a commit fires hooks, a trusted VS Code runs `.vscode` tasks, a devcontainer reopen runs `initializeCommand` on the host, Claude Code loads `.claude/` hooks and `.mcp.json`. So `podman_run` overlays each of `WORKSPACE_GUARD_ENTRIES` in [bin/konrad](bin/konrad) read-only (via `ro_bind`) on top of the writable workspace bind; the list follows Anthropic's [sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime) deny list, widened to whole entries. Three rules make it a boundary rather than a speed-bump:

1. **Top-level entries only, each overlaid whole.** A mountpoint can't be renamed or removed (`EBUSY`), but a directory that merely *contains* one can, so a `.git/hooks` overlay falls to `mv .git x` plus a fresh `.git`, while a whole `.git` under the bind root can't be moved aside. The cost: the agent can't commit (reads still work); the agent prompt already says "never commit unless asked", and `KONRAD_WORKSPACE_GUARD=0` is the per-run opt-out.
2. **Existing, non-symlink entries only.** Overlaying an absent path makes the engine create a mountpoint in the user's tree; a symlink would bind whatever it targets, possibly outside the workspace.
3. **apple/container guards directories only.** Its binds reject a file source outright, so there `.mcp.json` and a `.git` *file* (worktree/submodule checkout) go unguarded.

The residual: that apple/container file gap, entries created during the session (a `git init`, a new `.vscode/`), nested repositories below the top level, symlinked entries, and anything the user deliberately runs (a `Makefile`, `package.json` scripts) — review the diff before running agent-touched code.

**The `context/` mount is a reference *substrate*, not a config layer.** A sibling of `org/`/`user/` under `~/.config/konrad/`, bound read-only at `/context` (named corpora in subdirs) so the agent can `rg` org/user-supplied material — a host-mirrored wiki, internal docs — with no network and no stored secret. It takes no part in the merge, is bound only when the dir exists, and is **agent-only**: in `home_mounts`, never `cfg_mounts`, because the firewall proxy derives its allow-list from `cfg_mounts` and has no business seeing reference material. A bind (not a baked-in skill) fits because a corpus is large, churny and re-synced host-side, and a mount stays fresh for free. Activation layers on top: passive (the `environment.md` `/context` hint), described (an `AGENTS.md` naming the corpus), or active (a *thin* org skill that **points at** the mount, never one that *contains* the corpus). If a corpus outgrows `grep`, the escalation is an MCP retrieval sidecar, deliberately out of scope. Mount *presence* is also the boundary an opt-in confidential tier would build on: "don't mount the dir" is a cooperation-free seal in a way "don't load a skill" is not.

**Resource caps are default-on and auto-scaled to the host, identical on both engines.** Every agent launch runs with a `--memory` / `--cpus` ceiling; unset, it's half the host RAM (clamped to `2G`–`8G`) and all but two cores (clamped to `2`–`8`), via `host_mem_mib` / `default_memory` / `default_cpus` in [bin/konrad](bin/konrad) (fixed `4G`/`4` fallback). Modest on purpose, so a bigger machine keeps headroom for a co-resident local model; docling fits comfortably. The default lifts Apple `container`'s 1G per-VM default, which OOM-kills docling, *and* bounds runaway usage on otherwise-uncapped Podman. `KONRAD_MEMORY`/`KONRAD_CPUS` pin explicit values, `0` disables a cap. The CPU cap is also exported as `OMP_NUM_THREADS`, since docling/torch otherwise self-throttle to 4 threads whatever the cgroup allows. (GPU acceleration is moot: torch is the `+cpu` build and the engines run a Linux guest.) On the shared-kernel Podman path the agent and proxy are further hardened: `--cap-drop=ALL`, `no-new-privileges`, and `--pids-limit` (default `1024`, `KONRAD_PIDS_LIMIT` overrides) to bound a fork bomb below the host's PID max; apple/container bounds these at its per-container VM. (A read-only root filesystem would go further; it isn't planned.)

### Egress firewall

**The agent has no direct route to the internet; a sidecar proxy is the only way out, and it forwards only an allow-list.** This closes the network as an exfiltration channel — a prompt-injected agent can't ship the workspace or the provider credentials to an arbitrary host.

- **Two networks, per run.** `bin/konrad` creates an `--internal` network (no route out) and a normal egress network. The agent joins *only* the internal one; the proxy joins both. So the boundary is enforced by the engine's networking, not by the agent's cooperation — the agent (uid 1000) can't reconfigure it. A Podman *pod* can't do this: pod members share one netns, so they'd share the same egress.
- **Same topology and the same security property on both engines** — enforcement lives in a container the agent can't reach, surviving a root-level agent compromise — **with fussier plumbing on apple/container,** all of it behind the `eng_*` wrappers, `fw_proxy_url()` and `fw_setup()`:
  - *Agent → proxy by IP, not hostname.* apple/container has no resolver on a custom net, so the agent is handed the proxy's internal-net IP (re-read each run; it changes on recreate). Podman serves the name over its internal DNS.
  - *The proxy's egress leg is the built-in `default` net.* A `container network create` network has **no DNS resolver and no NAT**; only the engine-managed `default` net resolves and reaches the internet. So the proxy is dual-homed on the custom internal net **plus `default`**; Podman keeps a dedicated, torn-down egress net, since every netavark network resolves and NATs.
  - *Attach order is load-bearing.* A container inherits its resolver from the **first** `--network`, and an `--internal` net contributes none, so `default` goes **first**. The agent stays internal-only and never resolves anything.
  - **Host-gateway seal (apple/container only).** Its `--internal` net is *host-only*: the vmnet gateway sits on the Mac, so a host service bound to `0.0.0.0` would be reachable **directly** at the gateway IP, bypassing the proxy (rootless Podman has no such route). konrad seals it: `bin/konrad` starts the agent as root with `CAP_NET_ADMIN` and hands its entrypoint the internal-net gateway, which the root prelude `ip route add blackhole`s before dropping to `node` with the capability stripped (shared `exec_as_node` in [image/konrad-privdrop.sh](image/konrad-privdrop.sh)). The blackhole is kernel state the dropped agent can't remove, so apple/container reaches **parity with Podman**: the only path to the host is back through the proxy, at the allow-listed `host.containers.internal`. The seal is **fail-closed** — if the gateway can't be read or the route won't install, the run aborts (`--no-firewall` knowingly opts out).
  - **Local-model host alias (apple/container only).** Podman injects `host.containers.internal` into the proxy's `/etc/hosts`; apple/container injects none and has no `--add-host`, so `bin/konrad` hands the proxy the `default` net's gateway (the Mac), and the proxy's root prelude (keyed on `KONRAD_HOST_ALIAS_IP`) writes the mapping before dropping to `node`. Any *other* host name or raw gateway IP stays default-denied.
- **A forward proxy, on purpose.** The agent gets `HTTP(S)_PROXY` pointed at the sidecar; opencode runs on Bun, which honours those for `fetch`. That keeps the agent capability-less — no `NET_ADMIN`, no nftables, no transparent interception. The proxy is [tinyproxy](https://tinyproxy.github.io/) (`apt`-installed into the one image, not a second artifact) with `FilterDefaultDeny` + an anchored host filter.
- **The allow-list is derived, not hand-maintained.** The proxy runs the *same* `merge-config.js` over the *same* layers the agent sees and extracts every `provider.*.options.baseURL` host. opencode's *built-in* providers carry no `baseURL`, so for those the proxy maps each provider the user has **connected** (`auth.json` — read-only, ids only, never the keys) or **declared** (a `provider` block / a `model` prefix) to a host through a baked map ([provider-hosts.json](image/konrad-defaults/provider-hosts.json), generated from models.dev by [scripts/resolve-provider-hosts.sh](scripts/resolve-provider-hosts.sh) and refreshed by the lock bot — the same "pin upstream data, bake the pinned copy" pattern as `image/locks/`). Unioned with a deliberately tiny baked floor — `host.containers.internal` (local models) and `registry.npmjs.org` (opencode's on-demand provider SDK adapters) — plus the org/user `allowed_hosts` files and `--allow-host` for a run. `models.dev`, PyPI and the open web are opt-in: a configured model runs without them. Running the proxy *from konrad's own image* is what makes the derivation free. Hosts, not IPs, because remote providers sit behind rotating cloud IPs. The derivation lives in **one baked script** ([compose-allowed-hosts.sh](image/konrad-defaults/compose-allowed-hosts.sh)) so it can't drift: the proxy anchors its output into the tinyproxy filter, and [image/entrypoint.sh](image/entrypoint.sh) inlines the same list into the agent's `instructions`, so the model knows which hosts a fetch can reach. The proxy stays the enforcing boundary; the inlined copy is a start-of-session hint.
- **Live-reload, so connecting a provider needs no restart.** The sidecar polls `auth.json` and, on change, rewrites the filter and signals tinyproxy (`SIGUSR1`, which reloads without dropping connections), so an in-session `/connect` of an API-key provider takes effect within seconds. An *OAuth* first-connect needs the host *before* `auth.json` exists, so the clean path is **`konrad connect`** (`do_connect` in [bin/konrad](bin/konrad)): `opencode auth login` with the firewall **off**, safe because no agent is in the loop. `--allow-host`/`--no-firewall` remain the escape hatch inside a normal session.
- **Default-on, with a clean bypass.** On for every `run`/`shell` launch; `--no-firewall` (or `KONRAD_FIREWALL=0`) restores the unrestricted path. The proxy + networks are per-run (`$$`-named) and torn down by an EXIT trap. Mechanism: [image/konrad-proxy-entrypoint.sh](image/konrad-proxy-entrypoint.sh) and `fw_setup`/`fw_teardown` in [bin/konrad](bin/konrad).

## konrad code

**A second mode on the same CLI, engine and image, with the opposite trade-off: an agent gets your data or the internet, never both.** `konrad` sees the user's files and context, so its egress is sealed to an allow-list. `konrad code <git-url>` runs a third-party coding agent (Claude Code first) on a repo that already lives on the forge, so its egress can be open. It's the place to run a coding agent in bypass mode, instead of a dev container, which is porous by construction (attached-IDE sockets, the host podman socket, a bind-mounted workspace whose files the host later executes); Docker Sandboxes' license rules out commercial use.

- **Nothing the agent writes reaches the host.** `do_code` in [bin/konrad](bin/konrad) passes only the URL string (plus the user's git name/email, for attribution) into the container: no workspace bind, none of `konrad`'s config layers, no `context/`. That removes the deferred-escape surface the [workspace guard](#state-secrets--isolation) can only narrow. The one host mount is the user's code layer, below, read-only. Three named volumes carry the state, plus the image store when nested: `konrad-code-<host>-<path>` (the clone and its token, per repo), `konrad-code-tools` (`~/.local`: the agent binary) and `konrad-code-config` (`~/.config`: its login and settings). `--profile` suffixes all of them, login included, so a first run can be rehearsed in isolation. The mountpoints exist node-owned in the image, so a fresh volume inherits that ownership although the container starts as root; `:nocopy` keeps Podman from seeding the config volume with opencode's baked config.
- **The user's code layer is a read-only bind, not a copy.** `~/.config/konrad/code/user/` mirrors `~/.claude` for the coding agent (`CLAUDE.md`, `skills/`, `agents/`, `commands/`, `rules/`), separate from `konrad`'s `org/`/`user/` because a coding agent and the coworking agent want different instructions.
  - `code_user_layer` binds it at `/opt/konrad-code/user` when it exists, and the entrypoint links its pieces into `$CLAUDE_CONFIG_DIR`: `CLAUDE.md` itself and the four folders one entry at a time, because Claude writes into them too (`skills/synced/`) and a read-only folder link would break that. A link replaces an entry of the same name in the volume: the layer is the one home for user-level config. Each start first drops the links the last one made, so whatever left the layer is gone from the session too.
  - `CLAUDE.md` rather than `AGENTS.md`, because Claude Code has no user-level `AGENTS.md` slot and the folders are Claude Code formats anyway. Passing the content through an environment variable was weighed and dropped: it caps out near 128 KB per value, which skills with scripts outgrow, while a bind carries a whole dir and stays live. The agent can't make a locked read-only bind writable, not even from a nested user namespace.
  - Guarded host-side, since open egress means whatever the dir holds can leak: a *symlinked* dir is refused (a link to `~/.claude` would hand over credentials and transcripts); symlinks inside it, which dangle in the container, and files node can't read without keep-id are flagged with a warning. On Podman it's relabelled shared (`ro_bind`).
- **Git is the only way back.** A per-project access token (role Developer, typed inside the container on first run, stored in the repo's volume via git's `store` helper) plus a protected `main` means the agent can push a branch and open a merge request (`git push -o merge_request.create`) and nothing more. The user reviews on the forge, CI runs on the runners, the user merges, and code reaches the host only through their own `git pull`. The first run clones; later runs only `git fetch`, never touching a working tree that may hold unpushed work. Each run asks GitLab's token self-lookup (`/api/v4/personal_access_tokens/self`) about the token, so a dead one surfaces before a push fails: a 401 re-asks, a missing `write_repository` scope or an expiry within 14 days warns, anything else (another forge, no network) skips.
- **The seal is IP-level, in the agent's own netns, not a proxy.** tinyproxy filters on the *requested hostname*, so with open egress any name that resolves to a private address (or a raw IP) would reach the LAN or host through it. So [konrad-code-entrypoint.sh](image/konrad-code-entrypoint.sh) starts as root, installs `unreachable` routes for private, CGNAT, link-local, multicast and reserved space (v4 and v6) plus the container's connected subnets and the host's own interface networks (read host-side by `host_ip_cidrs`, so a LAN on public addresses is sealed too) into a dedicated table, and adds a policy rule that consults it *before* `main`, so it beats even the connected route to the gateway.
  - The one exemption is DNS (53/udp+tcp) to the resolvers in `resolv.conf`, which sit in private space on every engine. It's port-scoped because gvproxy serves its port-forwarding API on port 80 of the same address. Public DNS instead was dropped: networks that block outbound UDP 53 break it.
  - On Podman the run pins `--network bridge` and sets `rp_filter=0` (as a `--sysctl`, since `/proc/sys` is read-only inside): netavark's loose reverse-path filtering dropped inbound packets mid-transfer once private space was `unreachable`.
  - The entrypoint then drops to node via `exec_as_node` with the bounding set cleared, so the rules are kernel state the agent can't remove, the same trust model as the apple/container host-gateway seal, and fail-closed the same way (a failed route or rule, or a routable private self-check address, aborts the run). No sidecar, no extra networks, and it covers every protocol (git over ssh, raw sockets), not just what honours `HTTPS_PROXY`. On Podman the start keeps only `NET_ADMIN` (routes), `SETUID`/`SETGID` (the drop) and `SETPCAP` (clearing the bounding set), with `no-new-privileges` and the pids cap.
- **The agent binary is installed on first use, never shipped.** Its license lets a user install it but not konrad redistribute it, so on the first run the entrypoint asks, then runs the vendor's official installer into the shared tools volume, where the agent also self-updates. The installer's ~240 MB download is a silent, timeout-less `curl`, so the entrypoint hands it a `CURL_HOME/.curlrc` (abort under 1 KB/s for 60 s) and shows progress from the download file; the vendor's script runs unmodified. Logging in once inside the container persists in the config volume (`CLAUDE_CONFIG_DIR`), so subscription logins work, not just API keys. The session is `claude --dangerously-skip-permissions`, no IDE attached. The two facts the agent can't discover itself (the git-only way back, the sealed LAN) go in Claude Code's managed instructions file, `/etc/claude-code/CLAUDE.md`, written by the root prelude so the agent can read but not change it; unlike `--append-system-prompt`, it also reaches server mode and the sessions it spawns in worktrees.
- **Nested containers are rootless, on by default, and never touch the seal.** `konrad code` gives the agent rootless Podman unless `--no-nested` turns it off for a run (see the nested-Podman block in [image/Dockerfile](image/Dockerfile)). Rootful nesting is out: it needs `NET_ADMIN` on the agent, which deletes the seal. Rootless keeps it: nested capabilities live in a user namespace that never owns the agent's netns, and nested containers (pasta, `--network host`, a nested bridge) egress through that same sealed netns. [scripts/probe-nested.sh](scripts/probe-nested.sh) proves it, including seal-removal attempts from node, userns-root and a nested `--privileged` container.
  - **What it takes:** `newuidmap`/`newgidmap` with *file capabilities* rather than Debian's setuid bit (the setuid binary opens `uid_map` as a non-owner, which the kernel refuses), so `no-new-privileges` goes for the run and `exec_as_node --keep-caps setuid,setgid` leaves exactly those two in node's bounding set; every other setuid bit is stripped from the image, and the mappers are inert on every other run. A real subordinate range (`node:1:999` + `node:1001:64535`, inside 0..65535 so it exists under a rootless outer engine; single-uid mapping can't build images that `chown`). On Podman: `SYS_CHROOT` (its seccomp allows `chroot` only with it), `/dev/net/tun`, `unmask=ALL` (the kernel refuses a nested `/proc` mount while any of it is masked) and `label=type:container_engine_t`; `containers.conf` drops default sysctls (read-only `/proc/sys`) and shares the UTS namespace (seccomp refuses `sethostname`). apple/container has no such flags, so the root prelude gets `SYS_ADMIN` for itself (the drop clears it) to open tun and unmount the masks.
  - **The store** is a per-repo volume at `/var/lib/konrad-containers` (outside `~/.local`; native overlay can't stack on the overlay rootfs), so builds stay warm and one repo's images can't poison another's; on apple/container it's an engine volume, since VirtioFS refuses the `chown` and the overlay's pivot dir. Podman never collects on its own and the volume has no size limit, so [scripts/build-image.sh](scripts/build-image.sh) removes the images a rebuild replaced and tags every intermediate stage, and each session start removes dangling images and buildah leftovers older than a day. The age spares a build another session is running in the shared store, which neither podman's mount state (per session, in `/tmp`) nor `--filter until` (ignored for storage containers) would; the cost is an untagged stage's cache in other projects' builds. A hard per-volume cap would need root on the host (XFS project quotas), so it's left to the host. A store an unconfined run filled carries the `unconfined_u` SELinux user, which the confined agent can neither copy up nor relabel, so the entrypoint resets such a store once — it's a cache.
  - **SELinux stays on, as `container_engine_t`,** container-selinux's type for engines inside containers. `container_t` refuses the nested `/proc` mount and the tun device; `label=disable` ran the agent `spc_t`, which on native Linux let a simulated escape read `/tmp`, `/etc/passwd` and the system D-Bus. `container_engine_t` keeps `container_t`'s wall towards the host: every permission it adds on a type outside the container is a mount operation (which the kernel still limits to userns-mountable filesystems) or fuse/devpts device use, plus rights over its own `container_file_t`, `cgroup` writes and kernel module auto-loading. Nested containers inherit the type. The type may only be entered from container files, so PID 1 is the image's own `catatonit` rather than the host binary the engine's `--init` mounts.
  - **Why it's the default.** Against the non-nested flags, nesting gives up `no-new-privileges`, the `/proc` masks and (via `container_engine_t`) adds module auto-loading; on apple/container, a VM per container, only the masks, tun and a userns `/proc` mount change. None of it touches what `konrad code` rests on — the seal, no writable host mount, git as the only way back — only the defence in depth around a container that already runs untrusted code with open egress: an unmasked `/proc` discloses host detail that helps a kernel exploit, module auto-loading widens the kernel surface, and the mappers' file capabilities become reachable (at most `SETUID`/`SETGID` in the container's own userns). A full escape still needs an unpatched kernel bug, and lands confined on an SELinux host or in the VM on macOS. Against that, most projects need containers sooner or later, and a session started from the phone can't choose its flags. A micro VM per session would move the relaxed flags onto a guest kernel; it isn't planned.
- **KVM is a per-run opt-in (`--kvm`), Podman on Linux only.** VM-heavy work falls back to emulation without `/dev/kvm`, many times slower, so `--kvm` passes the host's device into the session (the setup run, which starts no VMs, goes without). Opt-in rather than default because it adds a surface nesting doesn't: the host kernel's KVM code, reachable by a hijacked agent. The seal is untouched: a guest's user-mode networking runs as node in the sealed netns, and tap or bridge devices need `NET_ADMIN`, which node never holds. `code_kvm_check` refuses host-side when `/dev/kvm` is missing or not world read-writable (node runs as a subordinate uid the host sees as "other", and the image's groups don't include the host's `kvm` group, so systemd's default `0666` is what makes it work); the entrypoint opens the device as node, which also catches an SELinux refusal, and tells the agent in the managed note. Nested containers get KVM through a bind of the session's `/dev`, not `--device /dev/kvm`: a nested `--device` needs `mounton` on `kvm_device_t`, which `container_engine_t` lacks. apple/container's `container run --virtualization` is unprobed, so there `--kvm` refuses.
- **Parallel sessions are git worktrees of the one clone.** Agents need a shared forge, not a shared working tree, so a second `konrad code` on the same repo gets its own worktree (`/workspace/.sessions/<name>`) beside the clone, which stays the `primary` session's. Worktrees rather than a volume per session: they share the clone's objects and token, and git refuses one branch in two of them, the guard parallel agents need. `do_code` picks the session host-side from container names (`konrad-code-<pid>-<repo id>-<session>`): the pid keeps `sweep_orphans` working, and the engine listing covers both engines, which a lock file in the volume wouldn't (apple/container runs each session in its own VM). Without `--session` a run takes the clone while it's free, else the lowest free `s<n>`. When nested, images and layers stay shared and file-locked, but libpod's database must be per session: its run state and lock table live in each container's `/tmp` and `/dev/shm`, so two sessions on one database reset each other's containers and hand out the same locks ([scripts/probe-shared-store.sh](scripts/probe-shared-store.sh)). A non-primary session points `static_dir` and `volume_path` at `sessions/<name>/` in the store; on apple/container, where the store is a block volume one VM can attach, it gets a store volume of its own.
- **`konrad code up` keeps a repo up for sessions started from the phone or a browser.** `do_code_up` in [bin/konrad](bin/konrad) starts a detached container per repo (`run -d` without `--rm`, so a crashed one keeps its log) running Claude Code's server mode, `claude remote-control --spawn worktree --capacity <n> --name <owner>/<repo> --permission-mode bypassPermissions`, with the seal, token, volumes and nesting of a terminal session; each session started in the Claude app or at claude.ai/code gets a worktree in `<clone>/.claude/worktrees/`.
  - **Server mode runs as designed, with a session of its own,** titled `<owner>/<repo>`: server mode creates one in its directory so there's somewhere to type immediately, and resuming centres on it. The opt-out, `--no-create-session-in-dir`, makes a throwaway server that never reads or writes its resume record, so after any restart the app showed every earlier session as "environment deleted"; with the session, the next start reuses the environment. It takes one `--capacity` slot from the start (about 260 MB idle), so the default capacity is 4. konrad gives it no role of its own.
  - **It works in a worktree of its own, `/workspace/.konrad-up/<owner>/<repo>`,** because in the clone it would share a checkout with a terminal session. The path carries `<owner>/<repo>` because the resume record is keyed by directory in the config volume that every repo shares. A stop longer than the resume window (about four hours), such as a night's reboot, starts a fresh session.
  - **Sessions started from the app survive a crash, not a stop.** On SIGTERM (`down`) server mode stops their work and doesn't save them for the next start, contrary to Anthropic's docs; konrad doesn't work around it.
  - **One-time questions need a terminal, server mode has none,** so `up` first runs the image attached in a *setup* mode (`KONRAD_CODE_MODE` in [konrad-code-entrypoint.sh](image/konrad-code-entrypoint.sh)): token, clone, install, then one interactive `claude` for the login, folder trust (it follows the git repository, so the clone's worktrees are covered) and the bypass-mode warning (both appear even under `--dangerously-skip-permissions` and default to exiting), and one attached `claude remote-control` for its own "Enable Remote Control?", stopped as soon as the answer is recorded. Left unanswered, a detached server waits on stdin forever; the answer is `remoteDialogSeen` in `.claude.json`, which setup checks and the up container warns about. A marker in the repo volume skips the interactive run afterwards while the login holds.
  - **A restart loop keeps server mode up,** since it exits after about ten minutes offline and apple/container has no restart policy. The entrypoint waits on it in the background so a stop's SIGTERM reaches claude, which then removes its sessions' empty worktrees and keeps those with work; on Podman that forwarding needs `KILL` on the init (only the up container gets it; node's bounding set stays cleared).
  - **The container outlives the konrad that started it,** so its name carries no pid (`konrad-up-<repo volume>`, which `sweep_orphans` doesn't match; cut to 52 characters plus a checksum where apple/container's 63-character limit bites). A host-side marker under `~/.local/state/konrad/code-up/` records that the repo should be up and how: URL, profile, `--capacity`, `--no-nested`, `--kvm`, server-mode arguments, and `KONRAD_MEMORY`/`KONRAD_CPUS` when set. `konrad code ls` and a terminal `konrad code` notice one a host restart ended, and `konrad code up --all` starts every marked repo that isn't running, each as a konrad of its own, with its recorded flags.
  - **Starting at boot is one line the user adds, not something konrad installs:** a systemd user unit or a launchd agent running `up --all` (README), rather than per-repo units konrad would have to keep in step with the markers. `up` runs without a terminal only for a repo with a marker, and then skips setup; what setup guards against is caught by the entrypoint (a missing token or install fails the start) or retried by the restart loop (a lost login).
  - In the nested store it keeps its own container database as session `up`, a name `--session` refuses. Its sessions share one memory cap, so the default ceiling is 16G instead of 8G. The app names the device after the container's hostname, with no override, so the run passes `--hostname <owner>/<repo>` (terminal sessions `<owner>/<repo>-<session>`); a slash is no valid DNS name, but the kernel limits only the length. The setup run gets the same name, since Claude Code keys some one-time answers to the hostname. Podman refuses the flag when it shares its host's UTS namespace (konrad's own nested engine), and apple/container gets none until a probe shows it takes the flag.
- **Accepted residuals.** Open egress means the repo and the token can leak (fine for one's own code with a single-project, revocable token; not for repos containing secrets). The tools and config volumes are shared across repos, so a compromised session could tamper with them for the next repo's session. Parallel sessions on one repo share its volume and, when nested, its images, so they're one trust domain. A repo that is up takes instructions from wherever the user's claude.ai login does: anyone holding that login can start sessions in it that push with the repo's token. "LAN" is private address space, the connected subnet and the host's own networks; anything else on public addresses is internet. The image is the full konrad image with a different entrypoint; a slim dedicated image only if its size gets in the way.
- **konrad's own repo has no dev container, deliberately.** A dev container pins a hard-to-install toolchain, makes onboarding one click, and enables hosted environments like Codespaces; none applies here. The static gates fetch every linter at a pinned version through `uv`/`npx` ([scripts/check.sh](scripts/check.sh)), so the host toolchain is `uv`, `node`, `git` and the Podman a contributor needs anyway, and a dev container can't remove that Podman (driving it from inside one took a host-socket mount and path-mapping code that existed for one environment). The container-shaped need, the agent's toolset with nothing on the host, is `konrad code --shell`; editor comfort is a committed `.vscode/`. Revisit if outside contributors become regular, or the repo gains a native toolchain worth pinning.

## The planning contract

Two **independent** gates, baked into the agent prompt ([image/opencode/agents/konrad.md](image/opencode/agents/konrad.md)):

- **`.agent/task.md`** — when the task has *side effects* (file edits, state-changing commands). A binary check at first tool-selection, not a complexity prediction. The agent writes it *before* the first side-effecting call, in a fixed shape:

```markdown
# <task title>
## Understanding       — what the user wants, as I read it
## Plan                — 3–5 bullets (the path, not micro-steps)
## Success looks like  — how I'll know I'm done
## Decisions & findings — appended during execution
## Outcome             — what shipped, what didn't, caveats
```

- **`todowrite`** — for anything beyond a trivial single Q&A; opencode's live in-UI checklist.

`task.md` holds *what & why* (durable, survives context compaction); `todowrite` holds *where the agent is right now*. No overlap, no sync burden. The agent surfaces the plan inline and proceeds when confident, or asks via `question` when a wrong guess would be costly (ambiguous goal, irreversible step). The `quality-assurance` skill later reads `task.md`'s Plan + Success + Outcome to render its verdict.

## Build & reproducibility

**Every input is locked; a bot maintains the locks; the publish is smoke-gated.**

- Each input is digest- or version-locked in [image/locks/](image/locks/): base image, the `uv` source image, Python deps (`python.lock`), `opencode-ai`, `typst`, and the Docling model repos (`models.lock`, commit-pinned so the ~1.1 GB model layer stays byte-stable across rebuilds; one `COPY` layer per model, so a single-model update re-pulls only that model). apt packages float — they refresh whenever the base image bumps. The [image/Dockerfile](image/Dockerfile) top comment mirrors this list.
- The Python venv ships as **three `COPY` layers** (the `venv-split` build stage partitions it): torch (~700 MB), the large slow-moving numeric wheels (opencv/scipy/numpy/onnxruntime/sympy, ~450 MB), and the churny remainder (~360 MB). So the near-daily `python.lock` bump of a small pure-python dep re-pulls just the light layer, while torch and the numeric set dedupe.
- The GitLab `resolve-locks` bot re-resolves each upstream daily and opens an auto-merging MR **only when something moved**, so a rebuild fires only when there's something new; no scheduled rebuild. `main` takes no direct pushes, the bot's included (protected branch; *Pipelines must succeed*), so every commit on it passed `check` in an MR pipeline. Freshness is a bot plus upstream registries, not hand-tended bumps.
- **Reproducible layers** — CI builds with `SOURCE_DATE_EPOCH=0` + `rewrite-timestamp=true`, so byte-identical content yields byte-identical layer digests and users skip a re-download when nothing changed. Local `konrad-dev rebuild` writes `konrad:local`, separate from the published `:latest`.
- **CI runs on a GitHub mirror; the primary repo stays on `gitlab.git.nrw`** (one-way push mirror → GitHub Actions does build → smoke → publish to `ghcr.io/jlbauss/konrad`), because the image build needs privileged runners. gitlab.git.nrw has since turned out to offer them, so the build could move back and the mirror go (design and probes in the [ROADMAP history](https://gitlab.git.nrw/jbauss2/konrad/-/blob/7c4aaca0b01804e465d7980a3463674c9347996f/ROADMAP.md), *Collapse the two-forge setup*). The GitHub side takes no contributions — CI plus auto-mirrored releases only. (Contributor and release flow: [CONTRIBUTING.md](CONTRIBUTING.md).)
- Every image carries `/etc/konrad/build-manifest.json` (dpkg / npm / pip versions + build metadata); `diff` two `:<short-sha>` images' manifests to bisect a regression to its upstream cause.

## Distribution & updates

**konrad ships as two artifacts that version and update on independent channels.** The **CLI** (`bin/konrad`, a bash script) and the **image** (the canonical artifact, pulled from GHCR) drift by design — a CLI-only patch bumps `VERSION` without firing an image rebuild (the workflow's `image/**` paths filter), so `konrad --version` prints both.

- **The CLI updates through its install channel,** `curl|sh`. konrad never self-updates the CLI from a *background* process — rewriting the running script mid-flight is a footgun, and the install channel owns the binary. `konrad update` on a `curl|sh` install re-runs the installer, which fetches from `main`; a symlink (dev) install is left to `git pull`.
- **The image (and org layers) stay fresh via a throttled background refresh** — the piece an install channel can't provide for a ~1 GB GHCR image. Every launching verb calls `maybe_background_refresh` ([bin/konrad](bin/konrad)): at most once per `KONRAD_REFRESH_INTERVAL` (default daily), it fires a **detached** worker that pulls `:latest`, re-tags the local `konrad:latest`, and runs `org_sync_all`. The launch never waits on it and never fails because of it; the *next* launch picks up a newer image, announced in one line only when the pulled image's **content ID** changed.
- **Availability beats freshness.** The throttle stamp is written *before* the worker runs, so a failed or slow refresh still counts against the interval rather than retrying every launch, like an org sync keeping its last-good checkout. `konrad update` does the same refresh **synchronously and now**, plus the CLI. Worker output goes to `~/.local/state/konrad/refresh.log`, never the terminal.
- **The notice queue carries news from unwatched work to the next launch.** Org sync rides the background worker, so a layer's `post-sync` hook fires detached, its output going to the refresh log. The worker or a hook (via `KONRAD_NOTICE_DIR`) writes one `key: value` file per notice under `~/.local/state/konrad/notices/`; `launch_preflight` renders and deletes them (`notices_flush` in [bin/konrad](bin/konrad)). Each choice is load-bearing:
  - **Stateless:** a notice is rendered then dropped, and the next refresh re-creates it while the fault persists, so a fixed fault's notice disappears with nothing to acknowledge or migrate.
  - **Source by path, not by field:** a top-level file is `konrad`'s, an `org-<name>/` subdir is that layer's, so a hook can't forge konrad-branded text (its lines are sanitized and capped on render).
  - **A severity ladder that never breaks the launch:** `info` is one dim line, `warn` a framed block, `blocked` adds an Enter-to-continue *only* on an interactive stdin (never under a piped `konrad run`, `KONRAD_NO_NOTICES=1`, or a disabled refresh).
  - A non-zero hook that wrote no notice has its last output lines promoted into a `warn` attributed to the layer, so existing layers gain visibility with no change on their side.

**The desktop launcher is generated on-machine, not shipped.** `konrad install-desktop` writes a user-scope launcher (a freedesktop `.desktop` + hicolor icon on Linux; a `~/Applications/Konrad.app` bundle on macOS) whose action is `konrad scratch`, since a GUI launch has no project cwd and lands in the [ephemeral scratch workspace](#state-secrets--isolation).

- **One shared wrapper script** (`~/.local/share/konrad/launch.sh`) locates konrad (a GUI `PATH` often omits `~/.local/bin`), offers to `curl|sh`-install it if missing, then execs `konrad scratch`, so the behaviour lives in one place.
- **The TUI needs a terminal a GUI click doesn't provide.** Linux leans on `.desktop` `Terminal=true` (DE-dependent; `install-desktop` warns when no terminal launcher is found); the macOS bundle spawns one around the wrapper (Terminal.app by default; `KONRAD_TERMINAL` picks `ghostty`/`alacritty`/`iterm`, validated against LaunchServices at install, since macOS has no default-terminal setting).
- **One icon source:** the committed [`assets/konrad.svg`](assets/konrad.svg), installed verbatim on Linux and rasterized (via the committed PNG master and the preinstalled `sips`/`iconutil`) into the mac `.icns`; a `curl|sh` install fetches it from the repo (offline → generic icon, the launcher still works).
- **Regenerating is ask-free and choice-preserving,** because `konrad update` re-runs the installer, so the launcher step runs on every update. The opt-in question is asked only on a genuinely fresh install (the installer already knows, from its clobber check); a decline stands, with `konrad install-desktop` as the opt-in later. An upgrade runs `install-desktop --refresh`, which regenerates **only an existing launcher**, so wrapper fixes reach launchers on disk without creating one the user declined. The terminal choice is stored **in the launcher itself** (a `TERM_ID` line that `resolve_mac_terminal` reads back when `KONRAD_TERMINAL` is unset), so there's no state to write, migrate or leave behind; a recorded value that's no longer supported warns and falls back. Both back-ends build the icon into a temp and move it in only on success, so an offline refresh never downgrades a working launcher.

This is host-side GUI integration only — no sandbox, engine, or image involvement, like `konrad open`.
