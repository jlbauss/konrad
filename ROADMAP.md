# Roadmap

konrad is a personal tool, shared as it is ([README → Status](README.md#status)). This list holds **at most ten items**: what automates the maintainer's checks, what keeps konrad safe and working for its own use, and what makes it smaller. An item comes in only when the maintainer asks for it, and a new one replaces an old one. Two lists sit outside that cap: [upstream workarounds and limitations](#upstream-workarounds-and-limitations), and [what to delete](#delete-when-it-gets-in-the-way) when it gets in the way. Sizes are planning guesses, not commitments: `S` (hours), `M` (a day or two), `L` (several days). How the list is kept: [CONTRIBUTING → When to update what](CONTRIBUTING.md#when-to-update-what).

The longer backlog this replaced (58 items, cut on 2026-10-26), with every design note and probe plan, is [in the history](https://gitlab.git.nrw/jbauss2/konrad/-/blob/7c4aaca0b01804e465d7980a3463674c9347996f/ROADMAP.md); bring an item back from there when it's needed.

## Next

### Automate the maintainer's probes

*First, because every probe a machine runs is one the maintainer doesn't: the agents that build konrad should get the host-side answer themselves, from a job log, instead of handing over a runbook.*

- [ ] `M` **Host probes as jobs on a [Tart](https://github.com/cirruslabs/tart) runner, so an MR is tested on macOS and on a real Linux host before anyone merges it.** The box can't run macOS, and its Linux is a container, so the host-only checks (Apple's `container` paths, the seal on native networking, SELinux enforcing, systemd units and a reboot, the installer from the real forge) are the maintainer's today. A GitLab Tart executor on an Apple-silicon Mac gives each job a throwaway VM, so an MR's code never runs on the Mac itself, which a plain self-hosted runner would allow.
  - **macOS guest:** `container system start`, then the bats suites on the BSD userland, `./scripts/smoke-test.sh`, and `bin/konrad`'s firewall, seal and `konrad code` paths. Apple's `container` inside the VM needs nested virtualization (to my knowledge M3+ and macOS 15+ on the host, a Tart flag, macOS 26 in the guest).
  - **Linux guest (arm64) on the same runner:** Podman with SELinux enforcing, the seal probe ([scripts/probe-konrad-code.sh](scripts/probe-konrad-code.sh)), the nesting probe ([scripts/probe-nested.sh](scripts/probe-nested.sh)), a systemd user unit across a VM reboot (`konrad code up --all`). amd64 stays covered by CI's instance runners.
  - **Probes become scripts first.** A runbook in an MR description can't run as a job; each boundary probe the agents write goes into `scripts/probe-*.sh`, baseline included, so a job and a human run the same thing.
  - **Open:** Tart's licence terms; Apple's two-VMs-per-Mac limit caps concurrency; jobs queue while the Mac sleeps; which jobs run on every MR and which on demand; how the job's verdict reaches the MR (the public job log, which agents already read).
  - **Probe first:** one manual job in a macOS guest running `container system start` and the smoke test, then the same in a Linux guest, then MR-triggered.
- [ ] `S` **A capped provider key in `konrad code`, so an agent runs `selftest.sh`'s model stage itself.** Today the real-model run is always a maintainer probe. With open egress, safe means bounded, not unseen: a dedicated key on a hard spend limit (an OpenRouter key with a credit limit, or an Anthropic Console workspace with a monthly limit), short expiry, one cheap model, never the maintainer's own account.
  - **Likely zero code; probe first.** A one-time `konrad-dev connect` in a `konrad code --shell` session should persist the key in the per-repo store's `konrad-secrets` volume; pin the model with `KONRAD_SELFTEST_MODEL`. Only the primary session sees it (others get their own `volume_path`). Probe: the model stage SKIPs without a key, PASSes after `connect`, survives a session restart, is absent from a parallel session.
  - **Then docs:** the key as an accepted residual in ARCHITECTURE → konrad code; replace "the box holds no provider key, by design" in CLAUDE.md and CONTRIBUTING.
  - **Only if no provider offers a hard cap:** a credential-injecting sidecar like the forge-token one (new maintenance surface, so not by default).

### `konrad code`: safer and simpler

- [ ] `L` **Container per repo — terminal sessions join the repo's container (probed 2026-10-07: go).** Terminal sessions run inside the repo's `up` container (`<engine> exec -it … claude`, `claude --worktree` for parallel ones; `konrad code <url>` starts the container when it isn't up). That retires most per-session plumbing: the pid and session pick in container names, the `.sessions/<s>` worktrees, the per-session libpod `static_dir`/`volume_path` split, apple/container's per-session store volume (and `probe-shared-store.sh`), and PID-based reaping in `sweep_orphans`. Unchanged: the seal, the token, the volumes, the image.
  - **Costs:** one memory cap for all of a repo's sessions; an exec'd terminal session still ends with its terminal (`claude --continue` resumes it); setup runs once per repo instead of per session.
  - **Host Claude's background-session supervisor in the container, so closing a terminal stops losing work (found 2026-10-16).** Claude Code ≥ 2.1 runs agent-view sessions (`←`, `/background`, `--bg`) as workers of a supervisor per `CLAUDE_CONFIG_DIR`, built to outlive the terminal; in a `run --rm -it` session the supervisor dies with the container. Probed with a throwaway config dir and an all-processes `SIGKILL` as the teardown: a session idle at teardown comes back `done`; one mid-turn comes back `failed` (`claude stop` first gives `stopped`), its running tools gone; the transcript survives either way (`claude --resume <id>` and `--continue` restore the conversation, verified). With exec'd terminal sessions the supervisor lives in the up container and survives a closed terminal; check that a `down` or sweep stops its sessions with `claude stop` before the container goes.
  - **`down` kills leftover exec clients first.** A frozen `exec -it` client blocks removal exactly like MR !22's `run -it` client (`given PID did not die within timeout`), so `down` and any sweep kill them before stopping.
  - **Sessions are directories, built by a konrad `WorktreeCreate` hook** in managed settings under `/etc/claude-code/` (out of the agent's reach): it creates `<sessions>/<name>/{<repo>,…}` as worktrees of every repo and prints the project's path; `WorktreeRemove` removes them, keeping any with work. Server-mode and `--worktree` sessions both call it. The hook input differs from the docs: `WorktreeCreate` gets only `name` and `cwd` (derive the toplevel with `git -C "$cwd" rev-parse --show-toplevel`, branch `worktree-<name>`); `WorktreeRemove` gets `worktree_path`.
  - **Absolute paths for sibling repos.** A `--worktree` session refuses git aimed at another directory by a relative or computed path (`git -C ../lib`); a literal absolute path works. So the hook writes a `CLAUDE.md` into the session dir naming each repo's absolute path. Trust follows the git repository, so each added repo needs its own trust, given in the setup run.
  - **The repo's own session moves into the clone.** Server mode keeps a session of its own in its directory, the one it resumes after a restart ([ARCHITECTURE → konrad code up](ARCHITECTURE.md#konrad-code)); today it works in `/workspace/.konrad-up/<owner>/<repo>` because terminal sessions use the clone. If terminal sessions all move to `claude --worktree`, run the server in the clone and retire `.konrad-up`, so that session is the one working in the clone, as server mode intends. Since `konrad code <url>` then starts the server too, every repo opened in a terminal appears in the app with that session; the README should say so. Per-repo config (the next item) would make the `<owner>/<repo>` part of the path unnecessary: it only keeps repos apart in the shared config volume.
  - **Maintainer probes:** the whole shape on the host (`up`, a terminal session via `konrad code <url>`, a parallel one, a phone session, `down`); a real dropped SSH connection under an exec'd session; apple/container end to end.
  - **Docs:** ARCHITECTURE → konrad code (parallel sessions become worktrees in one container), README `konrad code` section.
- [ ] `M` **Per-repo config, one read-only agent binary (plan C, decided 2026-10-06).** `konrad-code-config` (`~/.config`: login, `settings.json` and its hooks, plugins, memory) and `konrad-code-tools` (`~/.local`: the `claude` binary and whatever the agent puts on `PATH`) are mounted read-write into every repo's sessions, so a compromised session can plant a hook, binary or wrapper that runs in the next project's session with that project's token, or swap the login (an accepted residual today; the weak link once a project holds several repos' tokens).
  - **Per repo:** `~/.config` and the rest of `~/.local` move into per-repo volumes (`konrad-code-<host>-<path>-config`, `-local`; `--profile` suffixes them). No seeding from the old shared volumes, which may be tampered with; the launch says they can be removed.
  - **Shared, read-only:** the binary (`~/.local/share/claude`; the `~/.local/bin/claude` symlink is made per run), mounted read-only through `ro_bind`'s per-engine choice, so it holds on apple/container too. Self-update off (`DISABLE_AUTOUPDATER=1`); konrad updates the binary in a short-lived container that mounts only the tools volume, on `konrad update` and at most daily on launch. The first-run install moves there.
  - **Login per repo (plan C).** Plan D, one `claude setup-token` shared read-only, is out: Remote Control needs a full-scope login ([docs](https://code.claude.com/docs/en/remote-control), read 2026-10-06), and a full login rewrites its credentials file, which a read-only mount refuses. Revisit only if a login per project proves a real burden — **it does (maintainer, 2026-10-16): many repos, and one login, one install and one config (settings, preferences) across them is what makes `konrad code` comfortable today.**
  - **Plan E to weigh against C: per-repo Claude state, one shared login.** What leaks across repos today is the state, not the login: the agent view lists every background session in the config dir ("across all your projects", [docs](https://code.claude.com/docs/en/agent-view)) because `jobs/`, `sessions/`, the supervisor and `projects/` all live in the one `CLAUDE_CONFIG_DIR`; the `/resume` picker already defaults to the current worktree. So point `CLAUDE_CONFIG_DIR` at a per-repo dir (in the repo's volume, so parallel sessions of one repo still list each other) and link `.credentials.json` and `settings.json` to one shared copy each; the binary stays shared read-only as above, and `CLAUDE.md`, skills, agents and commands already come from the host's code layer (`~/.config/konrad/code/user/`, linked in per run). That keeps a full-scope login (Remote Control), one `/login` and one config for all repos; it gives up C's guard against a session swapping the login or planting a hook in the shared `settings.json`, so only `~/.local` and the state end up per repo. A middle road: keep `settings.json` per repo but seed it from the code layer on each launch, so preferences stay shared and a planted hook doesn't travel. **Probe first:** whether Claude rewrites the credentials file in place (the link holds) or by rename (the link turns into a copy, and the next token refresh, which rotates the refresh token, logs every other repo out); and that two repos refreshing around the same time don't race. If the link breaks, a file bind mount of the shared file is the next try. Until then, the agent view's `Ctrl+S` groups sessions by directory.
  - **Constraints:** never set `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` or `DISABLE_GROWTHBOOK` in a session (either turns Remote Control off). Worth a probe: whether managed settings under `/etc/claude-code/` can refuse hooks from anywhere else.
  - **Probes.** Baseline: a file written to `~/.config` and `~/.local/bin` in project A's session is visible in project B's. Then: neither is; a write under `~/.local/share/claude` fails on Podman and apple/container; a tool the agent installs persists in A, absent in B; the updater moves both projects to a new version and the in-session updater stays quiet; B asks for its own login, A's still works, and in each `claude --rc` reaches `/rc active` and receives a phone message (maintainer). Note which first-run questions a fresh config re-asks.
  - **Docs:** ARCHITECTURE → konrad code replaces the shared-volumes residual; README covers the login per project.
- [ ] `M` **Keep the forge token out of the agent's reach (evaluated 2026-10-07: realistic).** Today the token sits in the repo volume (`/workspace/.git-credentials`): a hijacked agent can send it anywhere, and it outlives the session until revoked. Instead a sidecar holds it: a stock reverse proxy (nginx or Caddy, configured rather than coded) on a network only it and the session share forwards *this project's* git smart-HTTP paths (`info/refs`, `git-upload-pack`, `git-receive-pack`) and adds the `Authorization` header. The clone's remote becomes the sidecar's plain-HTTP URL: no TLS interception, no CA in the image; push options and the `remote:` MR link pass through as part of the git protocol.
  - **Gains:** a leaked token stops being a residual and dies with the session; the proxy refuses every other path whatever the token's scopes, which makes `read_api` safe to grant (pass exactly the pipeline, job-log and MR-comment `GET`s; confidential issues stay unreachable).
  - **Unchanged:** during the session the agent can still push any branch and open MRs; review and the protected default branch stay the gate.
  - **Open:** one sidecar per repo container (so after container-per-repo); a port-scoped seal exemption for its address, like DNS's; the token prompt and expiry self-check move out of the agent container, the token into a volume only the sidecar mounts; one route per repo once there are several; a second VM on apple/container.
  - **Probe first:** clone, fetch and push with `merge_request.create` through the proxy, MR link back; any other project or API path refused; the token absent from everything the agent can read.
- [ ] `S` **`konrad code` from Ghostty: `'xterm-ghostty': unknown terminal type`.** `do_code` passes the host's `TERM` through and the image has no terminfo for it, so `clear` and anything curses-based fails (seen 2026-10-01). Fall back to `xterm-256color` when `infocmp "$TERM"` fails in the entrypoint, or bake Ghostty's terminfo; check whether the `konrad` TUI has the same issue. Also seen 2026-10-19: multi-line pastes into a session's bash hang at the prompt, while single lines run (readline echoes them in its horizontal-scroll fallback, a sign it doesn't know the terminal); a paste replayed through a pty in the image runs under both TERMs, so check whether the fallback fixes it before looking further.

### Releases: fewer moving parts

- [ ] `M` **Versions from tags; users install releases, not `main`.** Today a bot commits `VERSION` and the CHANGELOG section after each merge through its own auto-merging MR, `konrad update` installs the CLI from `main` and the image from `:latest`, and the two drift: an image built from a merge keeps the version before that merge's release, and a release without image changes gets no image of its own.
  - **The shape:** on a merge to main, the `release` job (serialized with `resource_group`) runs git-cliff (`cliff.toml` as it is, `--bump` for the version) over the commits since the last tag; if there's something to release it creates the `vX.Y.Z` tag and the GitLab Release, notes included, and commits nothing. The GitHub build triggers on the mirrored tag and publishes `:X.Y.Z`, `:0.X`, `:latest` and `:<sha>`; a release without image changes copies the previous image's digest to the new tags instead of rebuilding. `install.sh` and `konrad update` fetch the CLI at the latest release tag and that release's image, so one version names the CLI, the image and the notes, and rollback is installing an older tag.
  - **Deletes:** `VERSION`, `CHANGELOG.md` (the Releases page is the changelog), `scripts/release.sh`, the `release-mr` job and its bot branch, the CHANGELOG parsing in the `release` job and in `mirror-release.yml`, the CLI/image drift rules, and reading `VERSION` in a checkout (`git describe --tags` instead).
  - **Lock bumps release too:** the locks bot commits `fix(deps)`, so an opencode or base-image bump becomes a patch release with a note, instead of reaching users unannounced through `:latest`.
  - **Open:** the README badge (a shields GitLab-release badge); whether `mirror-release.yml` is still worth it on a CI-only mirror; how a pre-1.0 `--bump` treats `feat` (`features_always_bump_minor`).
  - **Maintainer probes,** since it rewrites the installer and the update path, on Linux with Podman and on macOS with `container`: a fresh install from the latest release; `konrad update` from today's install (which reads `main`) onto a release; a second `konrad update` once a newer release is out.

### Keeping up with upstream

- [ ] `M` **Bundled skills from upstream, pinned and unpatched.** Today every skill is a hand copy with no pin, so drift is invisible: `frontend-design` says "vendored verbatim" while upstream has since rewritten it, and Matt Pocock's repo has replaced `grill-me` with `grilling` and dropped `write-a-skill`. Instead a `skills.lock` (`<name> <repo> <sha> <path>`) feeds a build stage that fetches each skill at its commit; the lock bot bumps the shas like `models.lock`'s.
  - **Upstream skills stay byte-identical; konrad's additions move out of them.** The quality-assurance rule already lives in [konrad.md](image/opencode/agents/konrad.md) for every deliverable, so the per-skill quality-assurance sections go; their format-specific checklists move into the `quality-assurance` skill as one reference per format. Where an upstream skill expects something, adapt the image to the skill, not the skill to the image: bake what it uses when that's cheap, and say once in [environment.md](image/opencode/instructions/environment.md) what isn't there.
  - **The adapter in environment.md, one block for every upstream skill:**
    - Dependencies are baked: run skill scripts with `/opt/venv/bin/python`; skip a skill's `pip install`, `uv run` or `npm install -g` steps (they can't reach the network).
    - Skills written for other agents name their tools: `read_file` → `read`, `write_file` → `write`, `terminal`/`execute_code` → `bash`, `web_extract` → `webfetch` (allow-listed hosts only), `vision_analyze` → render to PNG and `read` it (needs a vision-capable model; otherwise say the visual check was skipped).
    - Not available, with the replacement: `marker-pdf` and OCR → the `docling` skill; `nano-pdf` (calls a hosted model) → edit with the `pdf` skill's scripts; PDF generation → Typst.
  - **Findings, researched 2026-10-18:**
    - `spreadsheets` → hermes-agent's **`xlsx`** (below; decided 2026-10-18). Trade-off taken knowingly: openpyxl drops charts and images when an existing workbook is re-saved (its own pitfalls section says so); `minimax-xlsx`, which edits the XML directly, avoids that but has been idle upstream since 2026-04 and is harder going for small models.
    - pdf EXTRACT ([extract.md](image/opencode/skills/pdf/extract.md)) → **docling's own skill**, which ships inside the docling wheel (`docling/.agents/skills/docling/`, MIT; present in the locked `docling-slim` 2.140.0) and covers reading PDF, DOCX, PPTX, XLSX, HTML and images. Copy it from the venv at build time: no lock entry, `python.lock` pins it.
    - `frontend-design` → [anthropics/skills](https://github.com/anthropics/skills) (Apache-2.0), current version. Anthropic's `pdf`, `docx`, `xlsx` and `pptx` skills are source-available under terms that forbid redistribution, so they're out.
    - `grill-me` → **`grilling`** ([mattpocock/skills](https://github.com/mattpocock/skills), MIT), general-purpose as it stands.
    - `write-a-skill` → pinned at the last upstream commit that has it (upstream removed it). Anthropic's `skill-creator` (Apache-2.0) is the maintained alternative but drives `claude -p` for its evals, so it doesn't fit opencode.
    - `image-editing` → [jlouage/Image-Editing-Claude-Skill](https://github.com/jlouage/Image-Editing-Claude-Skill) (MIT, one maintainer) unpatched: its font fallback finds DejaVu once `fonts-dejavu-core` is in the image, and the venv adapter above replaces the `uv run` patch.
    - **The office suite, including the Word and slides skills konrad lacks: [NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent)'s `docx`, `powerpoint`, `xlsx` and `pdf`** (`skills/productivity/`, MIT per skill, maintained: commits through 2026-10; all four taken, decided 2026-10-18). Independent of Anthropic's proprietary set (different structure, own CLIs). Built on python-docx, python-pptx, openpyxl, pypdf, pypdfium2, reportlab and LibreOffice, all already baked; their 83 tests pass against `python.lock`'s versions (run 2026-10-18). They name Hermes's own tools, which the adapter above maps.
    - **pdf → hermes's `pdf`, with the image made to fit it:** it replaces konrad's EDIT and FILL routes (merge, split, rotate, encrypt, metadata, images, fill and flatten, plus building new forms) and `minimax-pdf`'s fill scripts. Bake `pymupdf` and `pymupdf4llm` (~40 MB, AGPL-3.0 like konrad; `onnxruntime`, which `pymupdf4llm`'s layout step pulls in, is already baked) so its fast extraction path runs as written: with them installed its pdf tests pass and `extract_pymupdf.py` returns text and Markdown (checked 2026-10-18). Don't bake `marker-pdf`: 3–5 GB, it fetches its models on first use (offline here), and docling already does OCR and layout. Its OCR guide's `web_extract`/Firecrawl path is Hermes-only; the adapter routes it to docling.
    - konrad's own and staying: `quality-assurance`, `do-it-manually`, and a slim **`pdf-annotate`** skill (what's left of today's pdf skill: phrase-anchored highlights and real redaction by rasterizing, which hermes doesn't do). Its description must say "highlight, blacken, redact" so it doesn't compete with hermes's `pdf` for other PDF tasks. Later, offer it upstream to hermes-agent as a pull request; if it lands, konrad carries no pdf code of its own.
    - PDF generation → **Typst** with [lucifer1004/claude-skill-typst](https://github.com/lucifer1004/claude-skill-typst) (MIT, maintained), which targets Typst 0.15+ and ships API data for 0.15.1, the version `typst.lock` pins. Its `agents/` subagents are Claude-specific and can be left out. `#import "@preview/…"` packages download from `packages.typst.org`, which the egress floor refuses: allow-list it or note it in environment.md.

Smoke asserts every locked skill is present with valid frontmatter.

Per the [migration guide](https://opencode.ai/v2/docs/migrate-v1/), v2 still reads v1-shaped `opencode.json(c)` and `.opencode/` agents and skills; plugins, the server API and `tui.json` (now `cli.json`) break, none of which konrad uses.

Until then, re-check on each opencode bump.
  - **Do first:** the bundled-skills switch (above), so the migration doesn't also have to carry konrad's own skill copies. konrad keeps several org layers (decided 2026-10-18), so `merge-config.js` stays and the append rule below has to land there.
  - **The design question: `permission` becomes `permissions`, an ordered array** (`bash`→`shell`, `task`→`subagent`, `write`/`patch`→`edit`). [merge-config.js](image/merge-config.js) replaces arrays, so a layer or agent file that adds one rule would drop the whole baked list, secrets deny included, which breaks "agent files carry only deltas". Options: keep the v1 object shape for as long as v2 accepts it; or a merge rule for this one key (append in layer order, so later layers win under first- or last-match, whichever v2 uses). Decide before adopting any native v2 shape.

  - **Probe first, in the box:** build with `@opencode/cli` and today's config unchanged; then check what the guide doesn't cover: `opencode run` and its stdin handling, `opencode auth login` (`konrad connect`), the remote-MCP OAuth loopback port `konrad mcp-auth` publishes, the data dir and the `auth.json`/`mcp-auth.json` symlinks, the `instructions` globs the org-layer copy relies on, `opencode debug config` and `debug agent --tool` (the smoke guard), and v2's background service inside a `run --rm` container. Run the smoke guard against the v2 build first: it shows which keys v2 honours.
  - **Docs:** ARCHITECTURE → Configuration & instructions (merge rule, permission shape), environment.md, CLAUDE.md's quick facts on permissions.

## Delete when it gets in the way

*Candidates, not commitments: each goes when it next costs work, or never. Deleting beats replacing, since a replacement is new work of its own.*

- **The desktop launcher's extras.** `install-desktop` is ~430 lines of `bin/konrad` (terminal choice, AppleScript for iTerm, icon rasterizing, regeneration on every update). The smallest version that still works is a `.desktop` with `Terminal=true` on Linux and a `.command` file on macOS.
- **konrad's wrappers around opencode's own verbs.** `connect --custom` (~100 lines) and `mcp-auth` each wrap one opencode subcommand; a `konrad opencode <args>` passthrough with a small fail-closed table of sandbox settings would retire them (design in the history, *opencode's own verbs*).
- **The committed fonts (7.9 MB) and `scripts/fetch-fonts.sh`,** in favour of Debian's font packages, once PDF generation no longer needs reportlab's TrueType-only loading (details in the history, *Fonts from trixie only*).

## Upstream workarounds and limitations

*What an upstream bug costs konrad, kept so it can go once upstream moves. When konrad hits one, the maintainer decides: work around it (code konrad carries until upstream fixes it) or live with it (it stays broken, maybe with a hint in the docs). Either way it gets a bullet here, in the commit that adds the workaround or the docs, with the upstream link, what to check and what to remove. Re-check each one when its upstream ships a release; the goal is fewer workarounds, never more.*

### Workarounds

- **apple/container's pull starts over after a cut download** ([apple/container#2264](https://github.com/apple/container/issues/2264); fix in [apple/containerization#949](https://github.com/apple/containerization/pull/949), open). A pull gives up when the registry cuts a layer download midway and throws away the layers it already has; ghcr's CDN cuts slow downloads after a few minutes, so a slow link never finishes a large update. konrad's fallback, `container_pull_resumable` in [bin/konrad](bin/konrad), fetches the missing layers with resuming curl downloads and loads them with `container image load`. **Check:** a `container` release with #949 in it pulls through a cut download (throttle the Mac's link with Network Link Conditioner and run `container image pull` on a large image). **Remove:** the function and its two helpers, the `||` in `eng_pull`, [tests/pull-resume.bats](tests/pull-resume.bats) and [scripts/probe-container-pull.sh](scripts/probe-container-pull.sh).
- **The inline model-discovery probe** (opencode has no native `/v1/models` discovery: [opencode#27554](https://github.com/anomalyco/opencode/pull/27554), open). **Check** on each opencode bump. **Remove:** [discover-models.sh](image/konrad-defaults/discover-models.sh), its [entrypoint.sh](image/entrypoint.sh) block, the smoke assertion and the `KONRAD_NO_DISCOVERY` / `KONRAD_DISCOVERY_TIMEOUT` plumbing; keep its context-window handling if native discovery sets none for models outside the catalog (auto-compaction depends on it).
- **Nested `--device /dev/kvm` under `konrad code --kvm`** (container-selinux: `container_engine_t` may not `mounton` a `kvm_device_t`, AVC seen 2026-10-19; no upstream issue yet, [containers/container-selinux](https://github.com/containers/container-selinux) is where one would go). A nested `podman run --device /dev/kvm` fails with `crun: set propagation for dev/kvm: Permission denied`, so the managed note in [konrad-code-entrypoint.sh](image/konrad-code-entrypoint.sh) tells the agent to bind `/dev` instead. **Check** on a container-selinux release. **Remove:** that note line.

- **Clicking a link in the TUI does nothing** (the TUI captures the mouse: [opencode#44442](https://github.com/anomalyco/opencode/issues/44442), open; bare URLs carry no OSC 8: [#14966](https://github.com/anomalyco/opencode/issues/14966), fixed by [opentui#1261](https://github.com/anomalyco/opentui/pull/1261) but not yet in an opencode release). - **`konrad run` exits 1 on success under apple/container's egress seal** (last checked on container 1.2.0, no upstream issue). The engine reports a wrong exit code for the sealed shape (root, `NET_ADMIN`, an `--internal` network); a plain `exit 0` there also gives 1. Only scripted one-shots on macOS with the firewall on are affected; an init wrapper with a sentinel would be real machinery for an engine bug. **Check** on a `container` release: re-run a sealed `konrad run`.
- **The image's build date shows 1970** (`config.created`). Reproducible builds set `SOURCE_DATE_EPOCH=0`, and the build tooling sets `config.created` from the same value; the real build time is in `/etc/konrad/build-manifest.json` and the OCI labels. **Check** when the build tooling can set `config.created` on its own.
