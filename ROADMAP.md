# Roadmap & Backlog

Two horizons: **Next** (beta → 1.0) and **Later** (post-1.0). Raw ideas land in the Inbox; upstream-blocked items sit at the bottom. Every bullet is self-contained — reorder freely. Sizes are planning guesses, not commitments: `S` (hours), `M` (a day or two), `L` (several days), `XL` (a week+). Conventions for what lands here (vs. CHANGELOG or a commit message) are in [CONTRIBUTING → When to update what](CONTRIBUTING.md#when-to-update-what).

## Inbox

## Next — beta → 1.0

*The active backlog while the beta is public. Clearing it gates 1.0.*

- [ ] `S` **`konrad code` IPv6 probe.** The v6 routes the seal installs are still unprobed: no tested engine gives the container IPv6 — rootless Podman can't resolve AAAA, apple/container can't connect over v6 even unsealed, and on native Linux (Fedora, rootless Podman, 2026-09-30) the default bridge hands the container only a link-local v6 address, so even the unsealed baseline reaches no v6 target although the host has global v6. Probe on a host whose Podman network has IPv6 enabled (or with pasta as the agent's network): `./scripts/probe-konrad-code.sh podman`, and the v6 targets that connect unsealed must fail sealed. The other deferred probes passed on native Linux 2026-09-30: the seal (baseline host-LAN 200 → refused sealed, also from nested containers), a revoked project token, and `./scripts/probe-nested.sh`'s checks (cold nested build 505 s, smoke, selftest runtime path, store and cache surviving a restart).
- [ ] `S` **Decide whether `konrad code` nests by default.** With SELinux kept on (`container_engine_t`), what `--nested` still gives up on Podman is `no-new-privileges` (the uid mappers' file capabilities need it off) and the `/proc` and `/sys` masks (the nested `/proc` mount needs them gone, and the nested crun can't re-mask over them), plus `SYS_CHROOT` and `/dev/net/tun`; on apple/container only the masks. `./scripts/probe-nested.sh` prints that delta. If it's acceptable, make nesting the default with an opt-out; if a micro VM is wanted for the masks, the candidate is crun's libkrun handler (`--runtime krun`, needs `/dev/kvm`), so the relaxed flags land on a guest kernel as on macOS — opt-in only, with a container fallback.
- [ ] `S` **A capped provider key in `konrad code`, so an agent runs `selftest.sh`'s model stage itself.** Today the box holds no provider key, so the real-model round-trip is always a maintainer probe. Safe here means bounded, not unseen: with open egress whatever the agent can read it can leak, so the key gets the project token's treatment — a dedicated key on a hard spend limit (an OpenRouter key with a credit limit, or an Anthropic Console workspace with a monthly limit), short expiry, one cheap model, never the maintainer's own account. A leak then costs at most the cap until revoked; the IP seal is untouched (the provider is public) and the nested run keeps its own egress firewall.
  - **Likely zero code — probe first.** `selftest.sh` reads the shared `konrad-secrets` volume, which under `--nested` lives in the per-repo store, so a one-time `konrad-dev connect` (firewall off, no agent in the loop) in a `konrad code --shell --nested` session should persist the key; pin the model with `KONRAD_SELFTEST_MODEL` rather than a `user/opencode.jsonc` (`~/.config` is the cross-repo `konrad-code-config` volume). Only the primary session sees it — non-primary sessions get their own `volume_path` — so real-model runs are a primary-session thing. Probe: baseline the model stage SKIPs without a key, PASS after `connect`, still present after a session restart, absent from a parallel session.
  - **Then docs:** the key as an accepted residual in ARCHITECTURE → konrad code; replace "the box holds no provider key, by design" in CLAUDE.md and CONTRIBUTING with the setup and the capped-dedicated-key rule.
  - **Stronger, only if no provider offers a hard cap:** a host-side credential-injecting sidecar (the agent sends a dummy key over plain HTTP, the sidecar adds the real one and forwards only to the provider), so a compromised agent can spend the budget during the session but never take the key. Costs: a reverse proxy the image lacks (tinyproxy can't inject headers into `CONNECT`), a port-scoped seal exemption for private space like DNS's, and per-engine plumbing — new maintenance surface, so not by default.
- [ ] `L` **Several repos per `konrad code` session.** Work that spans repos ends today with the maintainer copying files between sessions and pushing by hand: a session holds one token for one repo, and [konrad-code-entrypoint.sh](image/konrad-code-entrypoint.sh) stores it for the host alone (`https://oauth2:<token>@<host>` in a `store` helper), so git sends it for every path on that host and a second repo, a submodule's included, is refused. The trigger is work that spans repos: a shared contract repo, a project that consumes it and a docs repo, on another forge than the project. Instead a project's sessions reach the repos the user added to it, each with its own token, cloned beside the project. The gate is the human typing a token: the agent can't create one, so it can't add a repo or raise a repo's access, whatever text it reads (decided 2026-10-06). Replaces the read-only-submodules item: a submodule is one more added repo.
  - **Grants per project, in the existing store.** `konrad code --with <url> <project-url>` asks once for that repo's token, stores it as one more line in the project volume's credential file and clones the repo; every later launch of the project fetches it, and `--without <url>` drops the line and the clone (refused while the clone holds unpushed commits). A grant holds for all the project's sessions, parallel ones included, until removed or revoked: no per-launch mounts or per-session credential files, which would add machinery to guard a choice the token already fixes. One token per (project, repo) pair, so each is revocable alone and a repo's log shows which project's sessions pushed. Relative URLs resolve against the project's, as in `.gitmodules` (`--with ../lib`); a repo on another host works, as lines are keyed by URL. The flags go before the project URL, since what follows it goes to `claude`.
  - **Credentials keyed by path.** Set `credential.useHttpPath` and key every line by its repo path, the project's own included. Probe the matching first: a stored line must match git's requests with and without `.git`, and existing files hold a host-only line that a path-keyed lookup may miss, so migrate it on the next start. `check_token`'s `sed` over the whole file and the "to add one: `rm $CREDS`" hint, which wipes every token, become per repo.
  - **Access is the token's; konrad reports it.** Each repo's access is permanent and chosen when creating its token: *read* (role Reporter, `read_repository`, or a deploy token) or *write* (role Developer, `write_repository`), either optionally plus `read_api`, which gives pipelines, job logs and MR comments on private repos (the review loop CLAUDE.md runs through public routes) but also confidential issues, where vulnerability reports go; the token question says so. konrad reads the scopes with the token self-lookup (a deploy token answers none and counts as read) and prints them in the startup lines and the prompt note (`lib: read · docs: write + read_api`); nothing is enforced on top. Every token gets the project token's self-check: a 401 asks again, an expiry within 14 days warns. No `api`: it adds approving MRs, creating pipelines and deleting branches, and nothing in this flow needs them.
  - **Protection check where the token can see it.** With `read_api`, konrad reads the default branch (`GET /projects/:id/repository/branches/<branch>`; probe that `protected`, `developers_can_merge` and `can_push` say what's needed) and warns when a write repo's is unprotected or the token could merge or push to it. Without `read_api` the API answers nothing for a private repo, and a test push would succeed exactly when the branch is unprotected, so konrad stays silent and the checklist lives in the token question and the README.
  - **GitLab checklist per write repo** (outside konrad; matters most for a repo whose merges deploy automatically): the default branch protected, "Allowed to merge" and "Allowed to push" Maintainers; the token's role Developer, never Maintainer; deployment secrets as **Protected** CI variables, since every branch the bot pushes runs a pipeline from its own `.gitlab-ci.yml` with the unprotected ones; approvals not counted as the gate. Lacking `api` doesn't mean the token can't merge: the push option `merge_request.merge_when_pipeline_succeeds` needs only `write_repository`, so the merge permission is the gate. gitlab.com's docs say project access tokens need Premium, but they work on Free in a personal namespace (observed 2026-10-06), not in a Free group; deploy tokens (Free, read-only by construction) are the fallback for read repos.
  - **Sessions become directories.** Today the primary works in `/workspace/<repo>` and a parallel session in a worktree at `/workspace/.sessions/<s>`. Instead a session is a directory holding every repo as a sibling: the primary's `/workspace/{app,lib,…}` (the clones), `s2`'s `/workspace/.sessions/s2/{app,lib,…}` (worktrees of them, created on first use). The agent finds the others at `../lib` in every session, and parallel sessions never share a working tree. Existing session worktrees move once (`git worktree move` to `.sessions/<s>/<repo>`); Claude keys its history by directory, so a moved session's `--continue` starts fresh. Shared with the detachable-sessions item: whichever lands first does the move. Sessions started through `konrad code up` don't fit this layout as is: Claude puts their worktrees in `<clone>/.claude/worktrees/<name>`, where `../lib` doesn't resolve; a `WorktreeCreate` hook building the session directory is the candidate fix, probed in the container-per-repo item.
  - **Fetch, never move.** Each launch fetches every repo and leaves the working trees alone, as for the project today. A fresh clone or worktree runs `git submodule update --init` (top level, the pinned commits); a later launch initializes only submodules not checked out yet. A submodule whose repo has no token gets a one-line hint (`add it with --with <url>`) instead of a question, so no file in a repo can trigger a token prompt.
  - **Agent and docs.** The prompt note lists each repo with its path and access, says pushes to read repos fail and that switching branches needs `git submodule update`, and how to reach a `read_api` token (`git credential fill`, no second copy). README's `konrad code` section: `--with`/`--without`, the access levels, the checklist. ARCHITECTURE → konrad code: grants per project and the human-typed token as the gate; the residuals that a read repo is still an injection source for every write repo in the session (review is the gate) and that a private read repo's content can land on a public write repo's branch before review; and, until the per-repo config item lands, that a hook planted in the shared config volume still reaches another project's tokens.
  - **Probes** (fixture: a project and a second repo on gitlab.git.nrw, a third repo on gitlab.com, each with its own tokens). Baseline: on `main` a clone of the second repo fails with the project token alone, and its own token clones it with a plain `git clone`. Then: `--with` asks once and clones beside the project, the next launch fetches without asking; the gitlab.com repo works beside the gitlab.git.nrw project; a read token's push is refused, a write token's push opens an MR via push options; the startup lines show read, write, `+ read_api` and a deploy token as read; with `read_api` the protection warning fires on an unprotected fixture branch and stays silent on a protected one; a pinned submodule is checked out with its token and hinted without one; `s2` gets `../<repo>` worktrees with no new question; `--without` refuses with an unpushed commit and removes line and clone without; a pre-change credential file still pushes the project; a line the agent adds for a repo using another repo's token is refused by the forge.

- [ ] `XL` **Detachable sessions — attach, detach, run in the background, in both modes.** A session lives exactly as long as its terminal today: `konrad` and `konrad code` run `<engine> run --rm -it`, so closing the terminal or dropping an SSH connection ends it (or wedges it — MR !22), and nothing can be started and left running. Instead every session runs detached, with the agent under [dtach](https://github.com/crigler/dtach) inside the container, and a terminal is only a viewer: launching starts and attaches, closing the terminal detaches, the agent exiting ends the session. With Claude Code's Remote Control (`claude --rc`), a `konrad code --background` session is then driven from claude.ai or the Claude app with no terminal at all (seen 2026-10-04: a dropped SSH connection took the session with it). A suspended host still runs nothing, so this covers a closed terminal or a laptop's SSH connection to an always-on host, not the host's own lid. One shared layer for both modes (decided 2026-10-05), built in two phases.
  - **Entrypoint:** both entrypoints end in one shared helper (beside `exec_as_node` in [konrad-privdrop.sh](image/konrad-privdrop.sh)) that runs the agent as `dtach -N <socket> -z` and passes its exit code on through a file, since dtach exits 1 regardless. The container lives exactly as long as the agent. dtach over tmux: 45 KB, no config, no key bindings beyond the detach key (`Ctrl-\`), and it leaves the terminal native (scrollback, mouse, copy), where tmux puts its own screen and scroll mode in between. What it lacks: no screen buffer, so a reattach repaints the live interface but doesn't replay earlier output (Claude's `Ctrl-O` transcript has it); no screen read, so konrad names the Remote Control session instead of reading its URL; no detach-others, so konrad clears stale viewers itself. Bake `dtach` into the image.
  - **Attach:** a shared helper run via `<engine> exec -it`: kill the session's other viewers (a dropped terminal leaves its in-container `dtach -a` behind, since the exec session keeps its pty open, and a stale one can't be told from a live one, so attaching takes the session over, like `tmux attach -d`), attach with a one-row size nudge (start a row short, grow back after ~0.5 s), and, when the session ended rather than detached (socket gone), exit with the agent's code. The nudge is needed because opencode and Claude Code both repaint only on a real size change: the SIGWINCH a plain `dtach -a -r winch` sends at an unchanged size draws nothing, and neither reacts to `Ctrl-L`. The exit code travels over `exec` because apple/container has neither `wait` nor an exit code in `inspect` (see Blocked); the entrypoint lingers up to 2 s for attached viewers to collect it.
  - **Session model** (lands with `konrad code up`, which needs it first): containers are named `konrad[-code]-<scope id>-<session>`, with no konrad pid: the scope is the repo for `konrad code` and the workspace dir for `konrad`, the sessions `primary`, then `s2`, `s3`, … as `konrad code` names them today. A launch starts a new session; `--session X` attaches to X when it runs, else starts it (today: refused); `attach` / `stop` act on the scope's only running session or need `--session`; `ls` lists all; `--background` starts without attaching. A launch notes sessions still running, so forgotten ones holding their `KONRAD_MEMORY` share don't pile up unseen. `--with`/`--without` (see the several-repos item) change the project's volume, so running sessions see them at their next start. A session is a directory holding the project and its added repos (also in that item); whichever item lands first moves the existing `.sessions/<s>` worktrees to `.sessions/<s>/<repo>`.
  - **Lifecycle:** the agent exits (`/exit`, a crash) → the container ends and is removed, an attached terminal returns with the agent's code, the worktree or workspace stays. The detach key, a closed terminal or a dropped SSH connection → the session runs on. `stop` → kill its viewers, stop the container. Host reboot or engine restart → the container is gone, the worktree stays, and `--session X` starts it fresh, with `claude --continue` for `konrad code`: per the Remote Control docs a continued conversation reconnects to the Remote Control session it recorded, so the phone keeps the same thread. The PID-based reaping in `sweep_orphans` goes; MR !22's lesson stays, generalised: any engine client that's alive but not reading blocks removal (`given PID did not die within timeout`), for an `exec -it` viewer as for `run -it`, so `stop` and the sweep kill a session's leftover viewers before removing it.
  - **Phase 1 — `konrad code` (`L`), on hold for the container-per-repo decision:** if that passes, phase 1 mostly goes (background work runs in `up` sessions). All of the above, plus Remote Control: `--background` implies `claude --rc "<repo> · <session>"`, foreground sessions take `--rc` after the URL as today. Setup happens in front of the user: `--background` stays attached through the first-run questions (token, `--with` repos, install, login, Claude's folder-trust prompt, the one-time Remote Control confirmation) and detaches by itself once the agent starts (the entrypoint writes a ready file just before `dtach -N`, and the attach helper exits on it), since a phone connects only once `claude` runs and can't answer them. Remote Control needs a claude.ai subscription login, not an API key or a `setup-token` token. Push notifications to the phone ("Push when Claude decides" in `/config`, persisted in the config volume) come for free and are worth a README line. Write the helpers, naming, verbs and sweep generic, so phase 2 is mostly the firewall.
  - **Phase 2 — `konrad` (`M`).** The opencode TUI the same way; `run` (piped one-shot), `connect` and `mcp-auth` stay plain `run --rm`. The firewall proxy and its two networks become per-session instead of per konrad process (`$$` names, torn down by the EXIT trap): torn down by the attached terminal when the session ends in front of it, else by the next launch's sweep, so an idle proxy lingers until then (a few MB on Podman, a small VM on apple/container). ## Blocked (externally)

- [ ] `S` **Retire the inline model-discovery probe when opencode ships native `/v1/models` discovery.** konrad ships an interim entrypoint-side probe ([discover-models.sh](image/konrad-defaults/discover-models.sh) + [entrypoint.sh](image/entrypoint.sh) §1c) that populates the model picker from each `baseURL` provider's `/models`. Re-check on each opencode bump. (If native discovery does NOT set a context window for catalog-absent models, keep whatever context-length handling the inline probe grew — auto-compaction depends on it.)
- [ ] `S` **Image build date shows 1970 (`config.created`).** Reproducible builds set `SOURCE_DATE_EPOCH=0`, so `podman images` / `docker inspect .Created` report the epoch. Verified (2026-06) that `config.created` can't be decoupled from the layer-rewrite epoch: dropping `SOURCE_DATE_EPOCH` re-stamps every layer to build time (breaks dedup), and the exporter's `source-date-epoch` attribute overrides `config.created` too — both knobs set one shared value. Only a post-build mutation of the config blob (layers left byte-identical) could give a real date — rejected as not worth the bespoke multi-arch tooling for a cosmetic field. The real build time still lives in `/etc/konrad/build-manifest.json` and the OCI labels. Revisit if the build tooling gains a way to set `config.created` independently of the layer epoch.
- [ ] `S` **`konrad run` exits non-zero on success under the apple/container egress seal — upstream `container run` bug.** On Apple's `container` engine (verified 1.2.0) a firewall-on one-shot `konrad run` answers correctly but exits `1`: the engine mis-reports the exit code for the agent's *sealed shape* (started `--user 0 --cap-add NET_ADMIN` on an `--internal` net, with the entrypoint's blackhole host-gateway route left in the netns at teardown). Confirmed engine-side, not konrad/opencode: opencode exits `0` inside the sealed container (`konrad shell` → `opencode run …; echo $?` = 0), a plain `exit 0` workload under the same shape still yields `container run` = 1, yet a normal unsealed container propagates faithfully (`exit 7` → 7). No clean konrad-side recovery — the true code isn't in `container inspect` (its `status` object has no exit field), and the seal route can't be torn down in-container (the node user's `CAP_NET_ADMIN` is stripped by design). Impact is narrow: only *scripted* one-shots on macOS + firewall (`konrad run … && …`, CI asserts); the interactive TUI and `konrad shell` are unaffected, and Podman is unaffected. Chosen not to work around (an init-wrapper + exit-code sentinel is real machinery + an image rebuild for an upstream bug). Revisit on an apple/container bump — re-run the sealed test and drop this if `container run` starts honoring the code, or wire `--cidfile` + `container inspect` if a bump exposes the exit code there.
