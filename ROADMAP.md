# Roadmap & Backlog

Two horizons: **Next** (beta → 1.0) and **Later** (post-1.0). Raw ideas land in the Inbox; upstream-blocked items sit at the bottom. Every bullet is self-contained — reorder freely. Sizes are planning guesses, not commitments: `S` (hours), `M` (a day or two), `L` (several days), `XL` (a week+). Conventions for what lands here (vs. CHANGELOG or a commit message) are in [CONTRIBUTING → When to update what](CONTRIBUTING.md#when-to-update-what).

## Inbox

*Raw ideas land here. Promote into Next or Later after a refinement pass.*

- [ ] `S` **Confirm `v*` tags still reach GitHub under the protected-branches-only mirror.** GitLab's docs don't say whether that mirror option still pushes tags, and [mirror-release.yml](.github/workflows/mirror-release.yml) recreates each release from the mirrored tag. At the next release: `git ls-remote --tags https://github.com/jlbauss/konrad | grep v<version>`. If it's missing, run the workflow's `workflow_dispatch` backfill and find out how GitLab decides which tags to mirror.
- [ ] `S` **`konrad code` from Ghostty: `'xterm-ghostty': unknown terminal type`.** `do_code` passes the host's `TERM` through, and the image has no terminfo entry for it, so `clear` and anything curses-based fails in the session (seen 2026-10-01). Fall back to `xterm-256color` when `infocmp "$TERM"` fails in the entrypoint, or bake Ghostty's terminfo; check whether `konrad` (the opencode TUI) has the same issue.
- [ ] `S` **Killing or closing an interactive launch can orphan its container.** Seen from the dev container (remote Podman client → rootful podman-machine socket), 2026-09-30: after a SIGTERM to the CLI *or* a closed terminal, the `--rm -it` container kept running — for `konrad --no-firewall shell` (the `exec` path) and `konrad code` alike, so it's not a `do_code` issue. Check on a native Linux and macOS host first; if it reproduces, the lightweight fix is probably `--sig-proxy` + a `SIGHUP` trap, or an `eng rm -f` of a `--cidfile` on EXIT.

- [ ] `M` **Keep SELinux confinement under `konrad code --nested`, then decide the default.** On Podman `--nested` adds `label=disable`, so the agent runs as `spc_t`. Probed on native Linux (Fedora, enforcing, 2026-09-30) as the agent's host uid (`subuid+999`), a simulated escape: under `container_t` (default `konrad code`) reading a world-readable `/tmp` file, `/etc/passwd` and the system D-Bus are all denied by SELinux; under `spc_t` all three are allowed, exactly as with no SELinux; `~/.bashrc` is denied in every case (file ownership, not SELinux). So on native Linux `--nested` trades SELinux's escape containment for nesting — it stays opt-in there until this is fixed (on macOS the trade stays inside the podman machine VM). The "label=nested isn't enough" comment in `do_code` was measured only in that VM. Try, on native Linux: `--security-opt label=nested` and `label=type:container_engine_t` (container-selinux's type for engines in containers — check it exists). Per candidate: **(1)** add it as a row to the `runcon` escape simulation (`setpriv --reuid=<subuid+999> … runcon system_u:system_r:<type>:s0:c1,c2 <cmd>`, with an unconfined row as the control) — it must deny like `container_t`; **(2)** a `PROBE_LABEL` knob in `scripts/probe-nested.sh` replacing `label=disable`, and `./scripts/probe-nested.sh podman --build` must still pass. A passing candidate replaces `label=disable` and reopens nesting-by-default. If none passes, try a micro VM before settling: run the `--nested` agent under crun's libkrun handler (`--runtime krun`, Fedora's `crun-krun`, needs `/dev/kvm`), so the relaxed flags land on a guest kernel as they do in the macOS VM, with no new engine or image. First check that libkrun's minimal guest kernel supports rootless nesting at all (user namespaces, overlay, `/dev/net/tun`, a nested `/proc` mount); then the seal, since it's policy routing in a netns that is now the guest's and krun's networking may differ from netavark/pasta: `./scripts/probe-konrad-code.sh podman` and `./scripts/probe-nested.sh podman --build` with plain `crun` as the baseline, then only the runtime swapped. It can only ever be an opt-in with a container fallback (no KVM on many cloud VMs or the GitLab runners). If neither passes, document the trade in the README and keep `--nested` opt-in on Linux.

## Blocked (externally)

*Items gated on an upstream change — either blocked awaiting a fix we've chosen not to work around, or an interim workaround to retire once upstream supersedes it. Revisit periodically.*

- [ ] `M` **`preserve_thinking` is a no-op through opencode — blocked on a reasoning field-name mismatch.** By design, `preserve_thinking` is a Qwen chat-template kwarg: the client passes prior reasoning back as a *field* on history assistant messages and the server template re-inlines it as `<think>` — so opencode's behavior (forward the kwarg, resend reasoning as `reasoning_content`) is correct-by-design. The blocker: vLLM ≥ 0.20 renamed the field to `reasoning` (RFC vllm#27755) and its input parser silently drops incoming `reasoning_content` (vllm#38488, open) — exactly matching the 2026-06-12 uzk-gpt/Qwen3.6-27B test (inline `<think>` honored, `reasoning_content` ignored). Unblocks when either **(a)** the endpoint's vLLM gains the input fallback (vllm#38488), or **(b)** opencode/AI-SDK emits `reasoning` (vercel/ai#6226, opencode#35283/#35284; qwen-code already shipped this client-side fix in its PR #4294) — else **(c)** document as a known limitation and drop the flag from the recommended config. Confirming probe (curl-only, next uzk-gpt access): replay history with reasoning under `reasoning` + `chat_template_kwargs.preserve_thinking: true`, with inline-`<think>` (known good) and `reasoning_content` (known bad) as controls. Changelog re-checked 2026-07-15 (v1.17.3 → v1.18.1): nothing relevant. Touches the "Local-model end-to-end shakedown" and A/B-test items' reproducibility needs.
- [ ] `S` **Retire the inline model-discovery probe when opencode ships native `/v1/models` discovery.** konrad ships an interim entrypoint-side probe ([discover-models.sh](image/konrad-defaults/discover-models.sh) + [entrypoint.sh](image/entrypoint.sh) §1c) that populates the model picker from each `baseURL` provider's `/models`. Upstream [opencode#27554](https://github.com/anomalyco/opencode/pull/27554) adds this natively (currently open/unmerged); when it lands, delete the probe, the entrypoint block, the smoke-test assertion, and the `KONRAD_NO_DISCOVERY` / `KONRAD_DISCOVERY_TIMEOUT` plumbing in [bin/konrad](bin/konrad), and revert the docs to native discovery. Re-check on each opencode bump. (If native discovery does NOT set a context window for catalog-absent models, keep whatever context-length handling the inline probe grew — auto-compaction depends on it.)
- [ ] `S` **Image build date shows 1970 (`config.created`).** Reproducible builds set `SOURCE_DATE_EPOCH=0`, so `podman images` / `docker inspect .Created` report the epoch. Verified (2026-06) that `config.created` can't be decoupled from the layer-rewrite epoch: dropping `SOURCE_DATE_EPOCH` re-stamps every layer to build time (breaks dedup), and the exporter's `source-date-epoch` attribute overrides `config.created` too — both knobs set one shared value. Only a post-build mutation of the config blob (layers left byte-identical) could give a real date — rejected as not worth the bespoke multi-arch tooling for a cosmetic field. The real build time still lives in `/etc/konrad/build-manifest.json` and the OCI labels. Revisit if the build tooling gains a way to set `config.created` independently of the layer epoch.
- [ ] `S` **`konrad run` exits non-zero on success under the apple/container egress seal — upstream `container run` bug.** On Apple's `container` engine (verified 1.2.0) a firewall-on one-shot `konrad run` answers correctly but exits `1`: the engine mis-reports the exit code for the agent's *sealed shape* (started `--user 0 --cap-add NET_ADMIN` on an `--internal` net, with the entrypoint's blackhole host-gateway route left in the netns at teardown). Confirmed engine-side, not konrad/opencode: opencode exits `0` inside the sealed container (`konrad shell` → `opencode run …; echo $?` = 0), a plain `exit 0` workload under the same shape still yields `container run` = 1, yet a normal unsealed container propagates faithfully (`exit 7` → 7). No clean konrad-side recovery — the true code isn't in `container inspect` (its `status` object has no exit field), and the seal route can't be torn down in-container (the node user's `CAP_NET_ADMIN` is stripped by design). Impact is narrow: only *scripted* one-shots on macOS + firewall (`konrad run … && …`, CI asserts); the interactive TUI and `konrad shell` are unaffected, and Podman is unaffected. Chosen not to work around (an init-wrapper + exit-code sentinel is real machinery + an image rebuild for an upstream bug). Revisit on an apple/container bump — re-run the sealed test and drop this if `container run` starts honoring the code, or wire `--cidfile` + `container inspect` if a bump exposes the exit code there.
- [ ] `S` **Clickable links in the TUI — blocked on opentui/opencode.** A plain click on a URL in the opencode TUI does nothing (e.g. an org skill's `Quelle: https://…` line): the TUI captures the mouse so the terminal never sees the click ([opencode#44442](https://github.com/anomalyco/opencode/issues/44442), open); bare URLs carry no OSC 8 hyperlink metadata ([#14966](https://github.com/anomalyco/opencode/issues/14966)), so the terminal's own URL detection breaks on wrap ([#51727](https://github.com/anomalyco/opencode/issues/51727)); Markdown links render as `label (url)` ([#45001](https://github.com/anomalyco/opencode/issues/45001)). [opentui#1261](https://github.com/anomalyco/opentui/pull/1261) (merged 2026-09-25) adds OSC 8 to bare and wrapped URLs but isn't in a release yet (latest 0.5.12), and opencode 1.18.33 (our pin) and its `dev` branch both still ship `@opentui/core` 0.4.5 — and even with OSC 8, #44442's mouse capture still eats the click.
